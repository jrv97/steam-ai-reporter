# Tag Kit for Steam UI design decisions (v1)

The choices behind `tokens.css`, `components.mdx` and `assets/icons/`, with the alternatives weighed, and what is still open. None of these is big enough for an ADR: the plan treats placement rules as tunable constants and copy changes as catalog edits. The published design system carries the same decisions.

## How the values were found

- Computed styles from live store pages on 2026-10-20, logged out, in English. At 1280px: the app page of 5072580, `/search/?term=ai`, a private wishlist URL and the home page. Then the app page of 1808500 for the notice bubbles, tag chips, corner flags and summary box (its tags block was not captured; see open question 16).
- The store's React pages ship their own scale on `:root` (spacing 4 to 32, radii 2, 4, 8, type 11 to 22, control heights 24, 36, 48), which became ours, so injected UI lines up with classic and React pages alike.
- Contrast uses the WCAG 2.x formula, compositing every translucent token over each sampled ground. Results are in the contrast section of `components.mdx`.
- Every page in `previews/` was rendered in Chrome: the compact badge over light, dark, striped, grey, sky and violet art, the list filter in both modes, and Spanish copy up to three times the English length.

## Decisions

1. **Match the store's look, carry no Valve branding.** Sampled neutrals, sizes and radii; "Motiva Sans" by name only. Rejected: using the store's brand assets (listings reject it, and it would look official); a fully foreign look (a seam on every page). The one Valve mark is the Steam glyph in the extension icon, wherever the icon is shown; no in-page component carries it (decision 40).
2. **Violet is the accent.** Rejected: teal (too close to the store's blue), amber or gold (collides with the store's own notices and reads as a warning), red or orange (reads as danger). Violet stays the default for every tag; decision 49 lets a person swap it per tag.
3. **Replaced by decision 36.**
4. **The compact badge sits top right on a solid surface.** The store's flags and live pill own the top-left and prices own the bottom edge. Rejected: a translucent or blurred surface (contrast depends on the art; blur is costly on carousels), bottom-left (where cover art puts the game's logo).
5. **Compact tiers are measured in script, not with container queries.** `container-type` would change how store containers size themselves.
6. **On search rows the full badge goes on the line under the title.** The title line clips.
7. **The banner sits above the purchase box, in a shadow root.** Rejected: the right column (326px wide, below the fold), under "About this game" (after the buying decision), a modal (what people asked to get away from), light DOM (store CSS styles bare `h2`, `p`, `button`).
8. **The banner attributes every word to the developer.** Nothing paraphrases or rates the notes.
9. **"Ignore this game", next to the store's own Ignore button.** The store's button sits just above. Ours only stops badges and the notice for one game in this extension and never calls the store's feature. The list is "Games you ignored" with "Stop ignoring".
10. **The list filter reads Show, Dim, Hide.** "Games that report AI use: Off" could read as turning the games off.
11. **Dim is opacity 0.4 only.** Rejected: grayscale (an effect layer per capsule, hundreds on a sale page).
12. **Settings are attributes on the root element; the list filter is pure CSS.** (Amended by decision 61: a change to the values a tag with facets picks draws the hosts again.) Rejected: toggling classes per host (one write per capsule, re-applied on every React re-render), inline styles (same cost, and they fight the store's).
13. **The banner collapses at 3 lines, without animation, and forgets the expanded state.**
14. **Replaced by decision 32.** The compact badge still takes the pointer only inside the capsule link.
15. **Settings pages are dark only, in a system font.** A light theme would need a second palette for no v1 gain.
16. **The 128px icon carries 16px of transparent padding** (Chrome Web Store guidance); 16, 32 and 48px are full bleed. The 16 and 32px renders are interim until hand-hinted reduced versions replace them.
17. **Tokens live on the store page's `:root`, all prefixed `sar-`.** Shadow roots inherit them.
18. **Every message is a catalog key** with a translator note. Labels that quote another label take it as a placeholder.
19. **Badges truncate; everything else wraps.** Rejected: shrinking type for long translations (unreadable at 11px), two-line badges (break the row rhythm, cover more art).
20. **Compact tiers depend on image size only,** so a capsule looks the same in every language.
21. **Logical properties and logical token names.** The switch thumb's `translateX` is the one physical value.
22. **A language picker on the full options page,** naming each language in itself through `Intl.DisplayNames`.
23. **Replaced by decision 41.**
24. **The prefix is `sar-`,** from the repo slug `steam-ai-reporter`, replacing the working name's `sfs-` before any code ships. Every class, attribute and custom property uses it.
25. **The banner is a store notice bubble in our hue.** Modeled on the DLC notice (`game_area_bubble`), sampled on 2026-10-20: a 135 degree wash at 80% from 10% to 100%, no border, radius or shadow, 8px 16px 12px padding, light Motiva type in `#d5d6d8`, the store's white-transparent button and underlined in-bubble links. Ours swaps the DLC plum for accent 800 to accent 600, keeps a 16px gap below (not 2px) so it never reads as part of the offer, sets the notes italic like the store's own disclosure section, and lifts the link color to `#d5d6d8` to stay AA. Its button matches the store's outlined buttons right below the banner: 11px regular, a 40% white edge, 2px 15px padding. It stays at least 24px tall for the target size, where the store's are 22px. The allow-listed note takes the DRM notice's geometry in neutral. Rejected: the first draft's card (a colored rule on one edge, 4px radius, drop shadow), which is generic callout chrome the store never uses; a neutral surface, which would pass as the store's own content; the DRM notice (one line, no room for notes or actions), the coming-soon and purchase boxes (rounded with shadows), the Early Access header (bordered), and the orange notice box (the store's warning tone, which judges).
26. **The full badge is a store tag chip in our hue.** Modeled on `.app_tag`: 19px tall, 7px padding, 2px radius, no border, a 20% tint. Text is accent 200 on accent 400 at 20%. It keeps the page font instead of the chips' Arial because it sits in Motiva rows. It carries no icon (decision 30); the violet hue and the wording set it apart from the store's blue tags, and it never sits in the store's tag row.
27. **The compact badge mirrors the store's corner flags.** Modeled on `.ds_flag`: 19px tall, square, solid, and 5px from the top and 5px from the end edge (amended 2026-10-26: it sat flush to the end edge, like the store's flags, which made the top and end margins unequal). Ours sits at inline-end with accent 100 on accent 900, plus a 1px accent 400 edge and an outer ring. Rejected: a mid-tone flag color (accent 700), which left mid grey art with no boundary at 3:1 (surface 2.54, edge 1.11) and violet art at 2.01.
28. **Backups are a file the person keeps.** (Built by decision 54, which leaves the lookup history out.) Download a JSON file; restore it after a check that shows its date and contents. Restore replaces settings and merges the game lists, so nothing on the current browser is lost. Full options page and userscript dialog only. Rejected: browser sync storage (stays within one browser family, needs a browser account, and its small quota cannot hold the lookup history); an account or server copy (the product sends nothing anywhere); a paste-in text box (clumsy for a large history); restoring the moment a file is picked (no chance to catch the wrong file). The check's Restore and Cancel row sits on the right with Restore first, like the store's own confirm dialogs.
29. **A summary-box row under Publisher, not a chip in the tag row.** (Superseded by decision 50: the row is gone.) The summary box at the top right is above the fold, while the banner usually is not. Steam's own reviews row there is a link that jumps to the reviews section, so a row whose violet chip jumps to our banner is a native pattern. Sampled on 2026-10-20: rows are flex label and value pairs in Arial 13/18, labels 35% wide, 11px uppercase. Rejected: first chip in the tag row (the row never wraps and Steam's own script hides tags that do not fit, so ours would overflow or force us to hide a store tag; it would also sit under "Popular user-defined tags" and read as a player tag); a floating bubble (covers content, against "never block"). The row holds only the badge label's chip, in the value column (decision 35).
30. **No icons in labels or the banner.** Badges, the tag section chips and the banner carry no spark or other icon. The store's own tags, corner flags and notice bubbles carry no icons either, and the violet hue plus the wording still mark our UI. Images under 180px wide get no compact badge, since that tier showed only the spark. Rejected: keeping the spark (dropped on 2026-10-20 in favor of labels without it); a short "AI" flag on small images (new copy, and a bare "AI" reads as a verdict rather than a report); squeezing the full label onto small images (it truncates to something like "AI use r...").
31. **The popup is flat and compact.** (Amended by decision 65: the toolbar popup is a row per tag with its name, list filter and master switch, and has no ignore lists, so the rule on an empty allow-list no longer applies; the flat look stays for the userscript dialog.) The toolbar popup shows its sections as flat groups split by a divider, captioned in small uppercase like the store's own section labels, with 4px rows and the store's 24px control height for the segmented control. An empty allow-list is left out there; the full page keeps its empty state. The full page keeps its cards, with 12px padding, 8px apart. Rejected: the same cards in the popup (padding and an empty card took most of its height); dropping the captions (the rows would lose their grouping).
32. **The badges' tooltip is a hover card built like the store's game hover popup.** One panel per page, sampled from `#global_hover` on 2026-10-21: `#344352`, the store's 20px shadow, 16px padding, 306px wide, square. It quotes the developer's notes verbatim, clamped to 6 lines, and names the AI service. Only the violet title marks it as ours. It sits 8px under the badge at z-index 2100, above the store's popup (1526), and it opens as a manual popover so it also clears the React hover layer, which sits in the browser's top layer, and a compact badge hangs it back over the capsule, away from where the store's popup opens. On the game's own page it drops the line that points to the store page (the summary row that once opened it is gone, decision 50). Rejected: the native `title` (cut at 200 characters, unstyled, delayed by the browser, and invisible to keyboard users); a custom tooltip without the store's surface (a seam next to the store's own popup); the store's arrow (ours sits right under its trigger); a violet accent edge (decision 30 removed edge chrome, and the violet title already marks it).
33. **The store's options arrow may cover the compact badge on hover.** On home capsules, `.ds_options` (z-index 15) appears in the badge's corner while the capsule is hovered and covers about 39px of its inline end. A store control wins over our label, the badge is clear at rest, and the hover card still opens from the uncovered part and by focus. Rejected: shifting the badge on hover (it jumps under the pointer) and a permanent wider inset (it reaches the store's top-left flags on small capsules). (amended 2026-10-26: curator pages, `store.steampowered.com/curator/<id>/`, carry the same kind of control, the store's grey three-dots button, in the capsule's top-right corner. It sits beside or over the chips, and on a capsule that also has the store's "IN LIBRARY" flag at the top left it touches the second chip. This is a known issue: the store's control stays on top and there is no workaround for now. The 39px figure predates the inset change of decision 27, which moved the group 5px away from the end edge, so the overlap is probably about 34px now (an estimate, not measured on a live page). The real fix, left for later, is to shift the group left of the store's control when it exists.)
34. **The store's game hover hides while the hover card is open.** On a search row the badge sits inside the row's link, so a pointer resting on it would open `#global_hover` beside the row and our card under the badge. While the card is open the root element carries `data-sar-hovercard="open"`, and one page rule sets `#global_hover` to `visibility: hidden`. Closing the card, `pagehide` and stopping remove the attribute, and the store's popup returns while the pointer stays on the row. It is the list filter's mechanism (decision 12): one attribute write and a CSS attribute selector, with no store node or script touched. The React hover layer gets no rule: it covers the capsule and takes the pointer, so the card closes after its grace, and its only hooks are a hashed class and `popover="manual"`, which our card shares. Rejected: removing or moving `#global_hover` (the store's script reuses that node on every row); `display: none` (it drops the popup's box while the store's script still places it); keeping the card off search rows (the notes would go unread there); leaving both open (two panels compete for one pointer).
35. **One label, "AI use reported", and a summary row with the chip alone.** (The summary row was replaced by decision 50.) Five surfaces named the verdict in four phrasings: "AI use disclosed" (full badge, hover card title), "AI disclosed" (compact badge), "Disclosed by the developer" (summary row chip, after an "AI use:" label) and "The developer discloses AI use" (banner heading). One catalog key, `badge_label`, now feeds all five; Spanish reads "Uso de IA declarado". The compact badge carries the full label: in the Arial fallback it grows from 71px to 87px, and on a 184px capsule it still leaves 33px beside a 64px store flag. The summary row drops its label column. Its chip starts 35% into the row, where Steam's labels end, so it shares the value edge of Developer and Publisher; the jump to the banner and the hover card stay. The developer stays named as the source: the hover card and the banner open with "In the developer's own words:" (decision 63 adds "According to Valve" for the entries Valve states). Rule 4 fixes the wording, so the choice has its own record: [ADR 0008 (one badge label)](../adr/0008-one-badge-label-ai-use-reported.mdx). Rejected: a short form for cover images (two labels again); "Developer reports AI use" (about 135px, which overlaps a store flag on a 184px capsule); a row label before the chip (it repeats the chip's first words).
36. **The mark is a Steam badge with a tag attached at its lower right** (decided 2026-10-24). The product tags Steam store pages with several kinds of fact: AI content disclosure, anti-cheat, third-party DRM, accounts and EULAs, and PvP. The old label tag with a spark named AI alone. The badge says where the tags live and the tag icon says what the product does, whatever the kind. The tag derives from Lucide's `tags` icon (ISC) and the badge from Simple Icons' Steam icon (CC0); the notices ship in `THIRD_PARTY_NOTICES.md`. Replaces decision 3. Rejected: keeping the label tag and spark, which names AI alone.
37. **The ring is as thick as the tag's stroke.** Both measure 20 units on the 300 unit canvas, so ring and tag sit at one line weight. The tag leaves a transparent cut 8 units wide around itself where it crosses the ring. A transparent cut keeps the mark clean on light and dark toolbars.
38. **Four files, one ink each.** `mark.svg` is the master and paints in `currentColor`; a page can theme it. `mark-purple.svg` (`#8f73f3`, `sar-accent-400`) is the extension icon, the store listings and the README logo; the PNGs render from it. `mark-white.svg` and `mark-black.svg` serve grounds that cannot take purple. `mise run icons` generates the three color files from the master, and a test keeps them equal. The files carry no `role`: each consumer adds its own role and name.
39. **Components still carry no icons.** (Amended by decision 65: the settings chrome has one icon, the popup's gear to all settings; store-page components still carry none.) Decision 30 stands: badges, the tag section chips and the banner have no icon, and neither the mark nor the Steam glyph enters them. Whether chips for the other tag kinds get icons is a later design decision; it needs its own record before any component takes one.
40. **The Steam glyph appears wherever the extension icon is shown, and in no in-page component.** This replaces the older statement that no Valve mark appears anywhere. The extension icon includes an outlined Steam glyph, which is Valve's trademark, by decision on 2026-10-24. The Steam glyph appears in the extension icon and wherever the icon is shown: the README logo, the store listing images, the options and popup headers and the design previews. It appears in no in-page component: no chip, badge, banner or hover card. No Valve wordmark, image or font file ships. The "not affiliated with Valve" lines stay in the settings, the README and the listings. Open question 6 covers the listing policies.
41. **The name is Tag Kit for Steam** (short name Tag Kit; the Spanish name is Tag Kit para Steam), a working name until a store search ends. The product tags several kinds of fact, and "AI Reporter" named only one. Our name comes first and "for Steam" says only what it works with, so it does not read as an official Steam product, the pattern of decision 23. The name lives in the catalog keys `ext_name`, `ext_short_name` and `ext_action_title`, so changing it is a catalog edit. The repo slug `steam-ai-reporter` and the `sar-` prefix (decision 24) stay. Replaces decision 23. Rejected: keeping AI Reporter for Steam, which names AI alone.

42. **One compact banner per app page.** One entry per disclosed kind with Steam's line as its h2 (24px for one entry, 18px for several) and an outlined "Ignore for this tag" button. Only AI keeps the developer's own text. A foot link, "Ignore this game", ignores every tag. Steam's own notice boxes already carry the details.
43. **An ignored scope becomes a note with Undo.** The region is named by its h2 when it holds one entry and no note, else "Declared by the developer", or "Tag Kit tags for this product" when an entry comes from Valve (amended by decision 63). Ignore and Undo buttons take their names from their own text and the heading or note (`aria-labelledby`).
44. **The summary row stays an AI summary.** It links to the banner when the banner holds the AI entry, else to the hover card. The hover card has no buttons. (Superseded by decision 50. The hover card still has no buttons.)
45. **The English app page draws AI from the live page at once.** Every other kind merges in when `GetItems` answers, and a failed request leaves the page as it is. When the live page and `GetItems` disagree on AI, `GetItems` wins and the disagreement is logged.
46. **Settings have one card per tag**, titled with Steam's line. (Amended by decision 65: the card sits in the tag's own tab beside what is ignored for that tag, and a tag that is off keeps its tab with only the master switch shown; the ignored lists are cards per scope, all tags in General.) The master switch hides the card's other controls. Writes patch what is stored at write time. The ignored list groups entries by scope, "All tags" first.
47. **PvP starts off.** It is common on rows and DLC, and the other six tags start on.
48. **Each tag's settings section closes, and remembers it.** (Superseded by decision 65: settings are tabs, nothing closes, and `v2:ui` holds the tab shown; the record below describes the first build.) Seven tag cards make the popup tall, and a person who sets up one tag rarely returns to it. A section is a native `details`: the browser gives the keyboard, the expanded state and the disclosure role, with no script or ARIA of ours. The summary keeps the tag's name and an "On" or "Off" cue for the master switch, which lives inside the card. Each section is remembered on its own, in a small separate `v2:ui` record shared by the popup, the page and the userscript dialog, and a section nobody toggled starts open. This differs from decision 13, where the banner forgets: the banner is a notice on a store page that should greet each visit, while settings are a place the person arranges once. Rejected: one open or closed state for all sections (hides what the person left open), remembering in settings (it is not a setting, and a backup would carry it), a button with `aria-expanded` and our own click handling (more code for the same result), animation (decision 13). Only the tag sections close; language, ignored games, backup and privacy are short and stay open.

49. **A tag can take a color of the person's choice (experimental).** (Amended by decision 65: the full help sits once in General and each field shows `options_color_help_short`, "Contrast is not checked. See General.", and points at the full help in `aria-describedby`; Reset is a quiet text button. Amended by decision 68: the swatch is now the browser's own color picker beside the hex text, which stays the readout, and the rejection of a native picker below no longer holds for that reason.) One hex color per tag kind, typed into a plain text box on the full options page and in the userscript dialog, not in the toolbar popup (its sections are already tall, and the popup is for quick switches). It accepts `#rgb` and `#rrggbb`, with or without the `#`, in any case, shows the error as it is typed and stores lowercase `#rrggbb`. The setting is labelled "(experimental)" in every language. It colors every surface that carries the tag: the full badge, the compact badge, the chips of the Tag Kit section, the hover card entry's title and the banner's wash. Unset, a tag looks as it did, with the same violet and the same contrast. This lifts the AA and 3:1 guarantees of the Contrast section for the people who pick a color, and only for them. Nothing clamps, nudges or checks the color: the picked color is the one used, and the help text says that contrast is not checked. Rejected: clamping or auto-adjusting a pick to keep AA (it would change the color the person chose, and the right amount depends on art and pages we do not control); a warning that blocks a low-contrast pick (a refusal the person did not ask for, with no good threshold across the full badge's grounds); a native color picker (a browser dialog that differs everywhere and cannot be typed into or read back by a screen reader as a code); a free choice of every shade (seven tags times seven shades is a form nobody finishes). It extends decision 2 and the Color section's "Violet is ours": the hue is ours by default and the person's by choice, never ours to judge with, so Principle 1 (label the report, never judge it) still holds. It follows decision 12 and Principle 7: the color is one custom property per kind on the root element (`--sar-kind-color-<id>`), never a per-node style. The chips and entries carry `data-sar-kind`, one hand-listed rule per kind reads that kind's property, and the shades are `color-mix()` of it at fixed shares that put the violet scale's shape on any color (the color plays accent 400; the full badge text is 37% of it into white, the compact surface 22% into black, the wash stops 31% and 66% into black at 80%). Custom properties inherit into the banner's and the dialog's shadow roots, so a change applies live and a chip is not drawn again. A banner with one tag takes that tag's color for its wash, and a banner that lists several keeps the default violet. Text on the banner, the switches, buttons and focus rings keep their tokens. Forced colors still override the badges. The userscript dialog gets the fields through a form capability (`colors`) apart from the layout context, so it keeps the popup layout. Open question 18 asks for the real contrast of a few popular picks.
50. **A "Tag Kit tags for this product" section below the user-defined tags, instead of one AI chip under Publisher** (decided 2026-10-25). Supersedes decision 44 and amends decisions 29 and 35. The summary row held one AI chip. Next to a banner that lists three kinds it looked like a bug, since the other kinds were missing, and it sat off the page's tag grid: a violet chip in a box of label and value rows. The section goes right below Steam's "Popular user-defined tags for this product:" block, with a small muted heading and the chips shaped like that row (19px, 2px apart, wrapping). It lists one chip for every disclosed kind that is enabled, not ignored and has its badge switch on, in registry order, all of them and with no "+N" chip, so a game that declares only kernel anti-cheat gets a section too. With no such kind there is no section and no heading. It is a block of its own with its own heading and hue, so decision 29's reason against the tag row (it never wraps, Steam hides the tags that do not fit, a chip there reads as a player tag) does not apply. Each chip opens the hover card with its own kind and does nothing on click: the jump to the banner went with the row, because one link cannot stand for several kinds and a card over the click path was why the two never combined. The section follows `.popular_tags_ctn`; without it, the last `.dev_row`; without both, nothing. Rejected: keeping the row and adding chips to it (still off the tag grid, and it repeats the banner under Publisher); chips in the store's tag row (decision 29); a "+N" chip (the section wraps, and a hidden kind is a kind the player never sees); a chip click that jumps to the banner (the same chip already opens the card, which quotes the developer, and four chips would share one target).
51. **DLC follow their base game's ignore, derived from Valve's parent field, with no list** (decided 2026-10-25). Ignoring a game for a tag, or for all tags, also ignores its DLC for that tag everywhere: the DLC rows of the base game's own page, the banner, search, wishlist and sale pages, and the hover card. Example: with AI ignored on ARC Raiders, the DLC rows on its page ("ARC Raiders - Frozen Trail Collector Set" and the rest) lose their AI chip and keep PvP, since only AI was ignored. The relation comes from the data the extension already fetches: a DLC item in GetItems carries `related_items.parent_appid`, the base game's app ID (captured for app 5201760, a DLC of 1808500, in `tests/fixtures/getitems/dlc-parent.json`). It rides the existing batch of up to 50 IDs, so it costs no request. The schema reads it as an optional branded `AppId` that degrades to no parent when missing or malformed, the verdicts of an app carry it as `parent`, and the verdict cache stores it (`CACHE_SCHEMA` 3 discards the entries written without it). One predicate, `isIgnored(ignored, id, kind, parent)`, decides for every surface. The ignored games list stays keyed by the games the person ignored, so no DLC appears in it, "Stop ignoring" on the base game restores the DLC, ignoring a DLC itself still works, and a DLC page whose base game is ignored for a kind shows no banner entry and no note for it. Unknown parent (not fetched yet, the HTML fallback, an item without the field) behaves as before. One level only, which is what Valve sends; the same field also names the parent of other child items such as a demo, and they follow it too. Rejected: a stored list of DLC IDs (stale the day a DLC ships, and a seed list rule 1 bans); reading the DLC page's "Downloadable Content for" link (one more page request per unseen DLC, against rule 13); reading the parent from the base game's page rows (covers only that page, not search, wishlist or a DLC opened directly); a second ignore entry per DLC written when the person ignores the base game (it never reaches a DLC released later and would fill the list the person reads).
52. **A bar in the look of the store's own search notice that counts what Hide removed, with a reveal for this page only** (decided 2026-10-25; amended 2026-10-26: the first build was one line in the banner's ignored-note look, and the maintainer asked for the store's bar look and wording). With a tag's list filter on Hide, results leave the list without a trace, and the setting lives in the popup. When at least one result in the current list is hidden, a bar of our own reads "4 titles have been hidden by Tag Kit based on your settings." with a "Show them" button; after a click it reads "4 hidden titles are showing." and "Hide them". The wording follows the store's own bar ("124 results match your search. 2 titles have been excluded based on your preferences."), and the Spanish follows its register. The bar names a number only, never a tag or a verdict (principle 1). It looks like the store's bar, sampled on the live search page on 2026-10-26 in Firefox: the store's `#search_results_filtered_warning_persistent` is a full-width flex row in the 876px results column with a 5px bottom margin, and its text cell has black at 20% behind `#fafad2` text, 10px padding and 12px Arial, Helvetica, sans-serif at a normal line height, with no radius and no border. Ours takes the same values from the `sar-store-notice-*` tokens, spans the column, leaves out the store's gear cell, and makes its button an underlined link in the sentence in the text's color, as the store's own "here" link. It goes right after the store's bar when the page has one (the `after` selector of the `LIST_PLACEMENTS` entry), else right before the result rows, and the two stack as one family. It stays a node of our own with our own classes: the store's node is never edited and its classes are never reused. The button has no 24px minimum any more: it is a link inside a sentence, which WCAG 2.5.8 exempts, and a taller button would make our bar taller than the store's. The reveal is one root attribute, `data-sar-reveal`, which the hide rules skip and the dim rules match, so the shown results come back dimmed, as a host that cannot hide does, and stay recognizable. Nothing is stored: a reload, a new list from the store, `pagehide` or the count reaching zero ends the reveal. The count is one `querySelectorAll` over the list for the hosts whose `data-sar-kinds` holds a kind the root's filters hide, run in one animation frame after a mutation that can change it (a `data-sar-kinds` write, a root filter write, a marked host leaving). It follows infinite scroll, settings, the ignore list and new verdicts without a scan pass or polling. A polite live region repeats the line once it has held for one second. Search comes first; another list surface is one `LIST_PLACEMENTS` entry. Library check: nothing adopted. `Intl.PluralRules` through the catalog's `plural`, the shared `announce` helper and one `MutationObserver` cover it, while announcer packages such as `@react-aria/live-announcer` assume React or add a second global live region. 54. **Backup and restore, as built: settings and ignore lists, merged, in one format for the extension and the userscript** (decided 2026-10-26). Builds decision 28 and settles open question 13. The file holds what the person set: each tag's switches, list filter and color, the language and the debug flag, and the three ignore lists (games, developers, publishers) by scope with their names and dates. It leaves out the lookup history, the open sections (`v2:ui`, decision 48), the breaker and the cache's meta record: the history comes from Valve's answers, refreshes itself, would be most of the file and would tie it to `CACHE_SCHEMA`. The file is JSON: `{ "format": "sar-backup", "version": 1, "created": <ms>, "settings": <the shape of v2:settings>, "ignored": { "games", "developer", "publisher": <the shape of v2:allow> } }`. Fields are named for what they hold, not for storage keys. The extension and the userscript store the same keys today (`v2:settings`, `v2:allow`, `v2:allow-developers`, `v2:allow-publishers`, each read through the same copy from `v1`), and either one reads a file the other wrote. A later `version` is refused with its own message; an earlier one passes through a list of upgrade steps, empty today. The file is untrusted: at most 1 MiB, checked on the size the browser reports before reading and on the text after, parsed to `unknown`, then read by the schemas that read storage (`parseSettings`, where a bad field takes its default, and `decodeScopes`, which drops a bad entry on its own), and a backup can hold nothing that storage cannot. Dropped entries are counted in the check and in the result. Every text from the file reaches the page through `textContent`. Restore merges each list (a union; where both sides list a game or creator in one scope, the entry ignored first stays, as components.mdx says, so restoring twice changes nothing) and then replaces the settings with one patch that names every field, which tells every settings subscriber. The lists go first: a failure part way leaves only additions, and the error says a retry is safe. After a restore the form draws its lists again itself, and on the options page the `storage.onChanged` path for `v2:allow` and the creator keys fires as well. Open store tabs take restored settings at once and restored lists on their next load, as with a list changed in another tab. A restored language reloads the options page, as any language change there does. The download and the file chooser sit behind a port, `FileTransfer`, with one implementation (`src/platform/shared/file-transfer.ts`, a Blob URL on `a[download]` and a hidden `input type=file`) kept in the page body on the options page and inside the dialog in the userscript, since the page around a modal dialog is inert. No permission, no request, no remote code; the code ships in `options.js` and the userscript only. Library check: nothing adopted. FileSaver.js (MIT, last release 2020) wraps the same Blob URL and anchor and adds fallbacks for browsers we do not support; browser-fs-access (Apache-2.0) adds the File System Access API, which Firefox lacks; a JSON schema validator would repeat the valibot schemas already in the bundle; `GM_download` would need a new grant. Measured: `options.js` 127,308 to 147,172 bytes, the userscript 259,792 to 279,609, `content.js` 193,262 to 198,433 (catalog text only); the budgets rise to 150, 284 and 200 KiB. Rejected: replacing the lists (it drops what was ignored only on this browser, against decision 28); the newest entry winning a conflict (the date reads as "since", which the first ignore keeps true); storage keys as field names (ties the file to the layout); keeping the history (above); one file per list (several picks for one move). Open question 12 (a "replace everything" choice) stays open.

55. **A lookup that failed or was held back is asked again, at most twice, once the breaker has closed** (decided 2026-10-26). A failed GetItems request opens the breaker for 60 to 70 seconds and stores the pause, which every tab honors, and a request cut off by a navigation counts as failed, because Steam's error answers reach `fetch` the same way. The next page then holds back every request, its uncached rows get unknown `rate-limited`, and nothing asked again: the scanner never finds a known host twice and the capsule UI detected each host once, which left those rows bare until a reload. Now the capsule UI and the app page's banner hand each answer to one helper, `createTransientRetry` (`detect/retry.ts`). When every kind of an app is unknown `error` or `rate-limited` (`isTransient`, next to `isStoredReason`), the item joins the next retry round. A round is one timer for all its items, started by the first item that joins it, and fires after the longest breaker pause plus one second (71 seconds, derived from `DEFAULT_BACKOFF`): by then the breaker has closed and the page memory entry (`TRANSIENT_TTL_MS`, 60 seconds) has expired, and the detector sends one GetItems request for the round's IDs. An item gets two retries at most, counted in a `WeakMap` keyed by its record; a host that left the page is skipped; a stored unknown (`gated`, `missing`, `malformed`) or any answered kind is never asked again before its TTL. `pagehide` and `stop` cancel the capsule UI's round, and `stop` cancels the banner's. The breaker is unchanged. Rule 13 bans polling, and this timer is not polling: a round starts only after a transient answer, asks only about the items that got one, checks no state on a schedule and ends after two rounds per item, while polling repeats with no event behind it. An app that the HTML fallback's per-page budget turned away also comes back `rate-limited`; its ID rides the next round's GetItems request, comes back `missing` and is turned away again, and the cap bounds that cost. Library check: nothing adopted. Retry packages such as p-retry wrap one promise in a backoff loop, while this needs one timer for many items, a per-item cap and the breaker's own pause. Rejected: waiting for the breaker to close (it is read only when a request goes out, and a pause stored by another tab would need a storage listener per platform behind a new port); retrying in the throttle or the chain (they see URLs and IDs, not the hosts that wait, and would ask for hosts that left the page); a shorter pause, or not counting a failed request (a change to the breaker, which guards against Steam refusing us); asking again on every rescan (the scanner does not rescan known hosts, and a page change is no reason to ask Steam).

66. **The tag order is a setting of the person's own, set by drag and drop in a Tag order card in General, with keys and clicks as alternatives** (decided 2026-10-26; amends decision 65's General list).
