# Tag Kit for Steam UI design decisions (v1)

The choices behind `tokens.css`, `components.mdx` and `assets/icons/`, with the alternatives weighed, and what is still open. None of these is big enough for an ADR: the plan treats placement rules as tunable constants and copy changes as catalog edits. The published design system carries the same decisions.

## How the values were found

- Computed styles from live store pages on 2026-10-20, logged out, in English. At 1280px: the app page of 5072580, `/search/?term=ai`, a private wishlist URL and the home page. Then the app page of 1808500 for the notice bubbles, tag chips, corner flags and summary box (its tags block was not captured; see open question 16).
- The store's React pages ship their own scale on `:root` (spacing 4 to 32, radii 2, 4, 8, type 11 to 22, control heights 24, 36, 48), which became ours, so injected UI lines up with classic and React pages alike.
- Contrast uses the WCAG 2.x formula, compositing every translucent token over each sampled ground. Results are in the contrast section of `components.mdx`.
- Every page in `previews/` was rendered in Chrome: the compact badge over light, dark, striped, grey, sky and violet art, the list filter in both modes, and Spanish copy up to three times the English length.

## Decisions

1. **Match the store's look, carry no Valve branding.** Sampled neutrals, sizes and radii; "Motiva Sans" by name only. Rejected: using the store's brand assets (listings reject it, and it would look official); a fully foreign look (a seam on every page). The one Valve mark is the Steam glyph in the extension icon, wherever the icon is shown; no in-page component carries it (decision 40).
2. **Violet is the accent.** Rejected: teal (too close to the store's blue), amber or gold (collides with the store's own notices and reads as a warning), red or orange (reads as danger). Violet stays the default for every tag; decision 49 lets a person swap it per tag.
3. **Replaced by decision 36.**
4. **The compact badge sits top right on a solid surface.** The store's flags and live pill own the top-left and prices own the bottom edge. Rejected: a translucent or blurred surface (contrast depends on the art; blur is costly on carousels), bottom-left (where cover art puts the game's logo).
5. **Compact tiers are measured in script, not with container queries.** `container-type` would change how store containers size themselves.
6. **On search rows the full badge goes on the line under the title.** The title line clips.
7. **The banner sits above the purchase box, in a shadow root.** Rejected: the right column (326px wide, below the fold), under "About this game" (after the buying decision), a modal (what people asked to get away from), light DOM (store CSS styles bare `h2`, `p`, `button`).
8. **The banner attributes every word to the developer.** Nothing paraphrases or rates the notes.
9. **"Ignore this game", next to the store's own Ignore button.** The store's button sits just above. Ours only stops badges and the notice for one game in this extension and never calls the store's feature. The list is "Games you ignored" with "Stop ignoring".
10. **The list filter reads Show, Dim, Hide.** "Games that report AI use: Off" could read as turning the games off.
11. **Dim is opacity 0.4 only.** Rejected: grayscale (an effect layer per capsule, hundreds on a sale page).
12. **Settings are attributes on the root element; the list filter is pure CSS.** Rejected: toggling classes per host (one write per capsule, re-applied on every React re-render), inline styles (same cost, and they fight the store's).
13. **The banner collapses at 3 lines, without animation, and forgets the expanded state.**
14. **Replaced by decision 32.** The compact badge still takes the pointer only inside the capsule link.
15. **Settings pages are dark only, in a system font.** A light theme would need a second palette for no v1 gain.
16. **The 128px icon carries 16px of transparent padding** (Chrome Web Store guidance); 16, 32 and 48px are full bleed. The 16 and 32px renders are interim until hand-hinted reduced versions replace them.
17. **Tokens live on the store page's `:root`, all prefixed `sar-`.** Shadow roots inherit them.
18. **Every message is a catalog key** with a translator note. Labels that quote another label take it as a placeholder.
19. **Badges truncate; everything else wraps.** Rejected: shrinking type for long translations (unreadable at 11px), two-line badges (break the row rhythm, cover more art).
20. **Compact tiers depend on image size only,** so a capsule looks the same in every language.
21. **Logical properties and logical token names.** The switch thumb's `translateX` is the one physical value.
22. **A language picker on the full options page,** naming each language in itself through `Intl.DisplayNames`.
23. **Replaced by decision 41.**
24. **The prefix is `sar-`,** from the repo slug `steam-ai-reporter`, replacing the working name's `sfs-` before any code ships. Every class, attribute and custom property uses it.
25. **The banner is a store notice bubble in our hue.** Modeled on the DLC notice (`game_area_bubble`), sampled on 2026-10-20: a 135 degree wash at 80% from 10% to 100%, no border, radius or shadow, 8px 16px 12px padding, light Motiva type in `#d5d6d8`, the store's white-transparent button and underlined in-bubble links. Ours swaps the DLC plum for accent 800 to accent 600, keeps a 16px gap below (not 2px) so it never reads as part of the offer, sets the notes italic like the store's own disclosure section, and lifts the link color to `#d5d6d8` to stay AA. Its button matches the store's outlined buttons right below the banner: 11px regular, a 40% white edge, 2px 15px padding. It stays at least 24px tall for the target size, where the store's are 22px. The allow-listed note takes the DRM notice's geometry in neutral. Rejected: the first draft's card (a colored rule on one edge, 4px radius, drop shadow), which is generic callout chrome the store never uses; a neutral surface, which would pass as the store's own content; the DRM notice (one line, no room for notes or actions), the coming-soon and purchase boxes (rounded with shadows), the Early Access header (bordered), and the orange notice box (the store's warning tone, which judges).
26. **The full badge is a store tag chip in our hue.** Modeled on `.app_tag`: 19px tall, 7px padding, 2px radius, no border, a 20% tint. Text is accent 200 on accent 400 at 20%. It keeps the page font instead of the chips' Arial because it sits in Motiva rows. It carries no icon (decision 30); the violet hue and the wording set it apart from the store's blue tags, and it never sits in the store's tag row.
27. **The compact badge mirrors the store's corner flags.** Modeled on `.ds_flag`: 5px from the top, flush to the edge, 19px tall, square, solid. Ours sits at inline-end with accent 100 on accent 900, plus a 1px accent 400 edge and an outer ring. Rejected: a mid-tone flag color (accent 700), which left mid grey art with no boundary at 3:1 (surface 2.54, edge 1.11) and violet art at 2.01.
28. **Backups are a file the person keeps.** Download a JSON file; restore it after a check that shows its date and contents. Restore replaces settings and merges the game lists, so nothing on the current browser is lost. Full options page and userscript dialog only. Rejected: browser sync storage (stays within one browser family, needs a browser account, and its small quota cannot hold the lookup history); an account or server copy (the product sends nothing anywhere); a paste-in text box (clumsy for a large history); restoring the moment a file is picked (no chance to catch the wrong file). The check's Restore and Cancel row sits on the right with Restore first, like the store's own confirm dialogs.
29. **A summary-box row under Publisher, not a chip in the tag row.** (Superseded by decision 50: the row is gone.) The summary box at the top right is above the fold, while the banner usually is not. Steam's own reviews row there is a link that jumps to the reviews section, so a row whose violet chip jumps to our banner is a native pattern. Sampled on 2026-10-20: rows are flex label and value pairs in Arial 13/18, labels 35% wide, 11px uppercase. Rejected: first chip in the tag row (the row never wraps and Steam's own script hides tags that do not fit, so ours would overflow or force us to hide a store tag; it would also sit under "Popular user-defined tags" and read as a player tag); a floating bubble (covers content, against "never block"). The row holds only the badge label's chip, in the value column (decision 35).
30. **No icons in labels or the banner.** Badges, the tag section chips and the banner carry no spark or other icon. The store's own tags, corner flags and notice bubbles carry no icons either, and the violet hue plus the wording still mark our UI. Images under 180px wide get no compact badge, since that tier showed only the spark. Rejected: keeping the spark (dropped on 2026-10-20 in favor of labels without it); a short "AI" flag on small images (new copy, and a bare "AI" reads as a verdict rather than a report); squeezing the full label onto small images (it truncates to something like "AI use r...").
31. **The popup is flat and compact.** The toolbar popup shows its sections as flat groups split by a divider, captioned in small uppercase like the store's own section labels, with 4px rows and the store's 24px control height for the segmented control. An empty allow-list is left out there; the full page keeps its empty state. The full page keeps its cards, with 12px padding, 8px apart. Rejected: the same cards in the popup (padding and an empty card took most of its height); dropping the captions (the rows would lose their grouping).
32. **The badges' tooltip is a hover card built like the store's game hover popup.** One panel per page, sampled from `#global_hover` on 2026-10-21: `#344352`, the store's 20px shadow, 16px padding, 306px wide, square. It quotes the developer's notes verbatim, clamped to 6 lines, and names the AI service. Only the violet title marks it as ours. It sits 8px under the badge at z-index 2100, above the store's popup (1526), and it opens as a manual popover so it also clears the React hover layer, which sits in the browser's top layer, and a compact badge hangs it back over the capsule, away from where the store's popup opens. On the game's own page it drops the line that points to the store page (the summary row that once opened it is gone, decision 50). Rejected: the native `title` (cut at 200 characters, unstyled, delayed by the browser, and invisible to keyboard users); a custom tooltip without the store's surface (a seam next to the store's own popup); the store's arrow (ours sits right under its trigger); a violet accent edge (decision 30 removed edge chrome, and the violet title already marks it).
33. **The store's options arrow may cover the compact badge on hover.** On home capsules, `.ds_options` (z-index 15) appears in the badge's corner while the capsule is hovered and covers about 39px of its inline end. A store control wins over our label, the badge is clear at rest, and the hover card still opens from the uncovered part and by focus. Rejected: shifting the badge on hover (it jumps under the pointer) and a permanent wider inset (it reaches the store's top-left flags on small capsules).
34. **The store's game hover hides while the hover card is open.** On a search row the badge sits inside the row's link, so a pointer resting on it would open `#global_hover` beside the row and our card under the badge. While the card is open the root element carries `data-sar-hovercard="open"`, and one page rule sets `#global_hover` to `visibility: hidden`. Closing the card, `pagehide` and stopping remove the attribute, and the store's popup returns while the pointer stays on the row. It is the list filter's mechanism (decision 12): one attribute write and a CSS attribute selector, with no store node or script touched. The React hover layer gets no rule: it covers the capsule and takes the pointer, so the card closes after its grace, and its only hooks are a hashed class and `popover="manual"`, which our card shares. Rejected: removing or moving `#global_hover` (the store's script reuses that node on every row); `display: none` (it drops the popup's box while the store's script still places it); keeping the card off search rows (the notes would go unread there); leaving both open (two panels compete for one pointer).
35. **One label, "AI use reported", and a summary row with the chip alone.** (The summary row was replaced by decision 50.) Five surfaces named the verdict in four phrasings: "AI use disclosed" (full badge, hover card title), "AI disclosed" (compact badge), "Disclosed by the developer" (summary row chip, after an "AI use:" label) and "The developer discloses AI use" (banner heading). One catalog key, `badge_label`, now feeds all five; Spanish reads "Uso de IA declarado". The compact badge carries the full label: in the Arial fallback it grows from 71px to 87px, and on a 184px capsule it still leaves 33px beside a 64px store flag. The summary row drops its label column. Its chip starts 35% into the row, where Steam's labels end, so it shares the value edge of Developer and Publisher; the jump to the banner and the hover card stay. The developer stays named as the source: the hover card and the banner open with "In the developer's own words:". Rule 4 fixes the wording, so the choice has its own record: [ADR 0008 (one badge label)](../adr/0008-one-badge-label-ai-use-reported.mdx). Rejected: a short form for cover images (two labels again); "Developer reports AI use" (about 135px, which overlaps a store flag on a 184px capsule); a row label before the chip (it repeats the chip's first words).
36. **The mark is a Steam badge with a tag attached at its lower right** (decided 2026-10-24). The product tags Steam store pages with several kinds of fact: AI content disclosure, anti-cheat, third-party DRM, accounts and EULAs, and PvP. The old label tag with a spark named AI alone. The badge says where the tags live and the tag icon says what the product does, whatever the kind. The tag derives from Lucide's `tags` icon (ISC) and the badge from Simple Icons' Steam icon (CC0); the notices ship in `THIRD_PARTY_NOTICES.md`. Replaces decision 3. Rejected: keeping the label tag and spark, which names AI alone.
37. **The ring is as thick as the tag's stroke.** Both measure 20 units on the 300 unit canvas, so ring and tag sit at one line weight. The tag leaves a transparent cut 8 units wide around itself where it crosses the ring. A transparent cut keeps the mark clean on light and dark toolbars.
38. **Four files, one ink each.** `mark.svg` is the master and paints in `currentColor`; a page can theme it. `mark-purple.svg` (`#8f73f3`, `sar-accent-400`) is the extension icon, the store listings and the README logo; the PNGs render from it. `mark-white.svg` and `mark-black.svg` serve grounds that cannot take purple. `mise run icons` generates the three color files from the master, and a test keeps them equal. The files carry no `role`: each consumer adds its own role and name.
39. **Components still carry no icons.** Decision 30 stands: badges, the tag section chips and the banner have no icon, and neither the mark nor the Steam glyph enters them. Whether chips for the other tag kinds get icons is a later design decision; it needs its own record before any component takes one.
40. **The Steam glyph appears wherever the extension icon is shown, and in no in-page component.** This replaces the older statement that no Valve mark appears anywhere. The extension icon includes an outlined Steam glyph, which is Valve's trademark, by decision on 2026-10-24. The Steam glyph appears in the extension icon and wherever the icon is shown: the README logo, the store listing images, the options and popup headers and the design previews. It appears in no in-page component: no chip, badge, banner or hover card. No Valve wordmark, image or font file ships. The "not affiliated with Valve" lines stay in the settings, the README and the listings. Open question 6 covers the listing policies.
41. **The name is Tag Kit for Steam** (short name Tag Kit; the Spanish name is Tag Kit para Steam), a working name until a store search ends. The product tags several kinds of fact, and "AI Reporter" named only one. Our name comes first and "for Steam" says only what it works with, so it does not read as an official Steam product, the pattern of decision 23. The name lives in the catalog keys `ext_name`, `ext_short_name` and `ext_action_title`, so changing it is a catalog edit. The repo slug `steam-ai-reporter` and the `sar-` prefix (decision 24) stay. Replaces decision 23. Rejected: keeping AI Reporter for Steam, which names AI alone.

42. **One compact banner per app page.** One entry per disclosed kind with Steam's line as its h2 (24px for one entry, 18px for several) and an outlined "Ignore for this tag" button. Only AI keeps the developer's own text. A foot link, "Ignore this game", ignores every tag. Steam's own notice boxes already carry the details.
43. **An ignored scope becomes a note with Undo.** The region is named by its h2 when it holds one entry and no note, else "Declared by the developer". Ignore and Undo buttons take their names from their own text and the heading or note (`aria-labelledby`).
44. **The summary row stays an AI summary.** It links to the banner when the banner holds the AI entry, else to the hover card. The hover card has no buttons. (Superseded by decision 50. The hover card still has no buttons.)
45. **The English app page draws AI from the live page at once.** Every other kind merges in when `GetItems` answers, and a failed request leaves the page as it is. When the live page and `GetItems` disagree on AI, `GetItems` wins and the disagreement is logged.
46. **Settings have one card per tag**, titled with Steam's line. The master switch hides the card's other controls. Writes patch what is stored at write time. The ignored list groups entries by scope, "All tags" first.
47. **PvP starts off.** It is common on rows and DLC, and the other six tags start on.
48. **Each tag's settings section closes, and remembers it.** Seven tag cards make the popup tall, and a person who sets up one tag rarely returns to it. A section is a native `details`: the browser gives the keyboard, the expanded state and the disclosure role, with no script or ARIA of ours. The summary keeps the tag's name and an "On" or "Off" cue for the master switch, which lives inside the card. Each section is remembered on its own, in a small separate `v2:ui` record shared by the popup, the page and the userscript dialog, and a section nobody toggled starts open. This differs from decision 13, where the banner forgets: the banner is a notice on a store page that should greet each visit, while settings are a place the person arranges once. Rejected: one open or closed state for all sections (hides what the person left open), remembering in settings (it is not a setting, and a backup would carry it), a button with `aria-expanded` and our own click handling (more code for the same result), animation (decision 13). Only the tag sections close; language, ignored games, backup and privacy are short and stay open.

49. **A tag can take a color of the person's choice (experimental).** One hex color per tag kind, typed into a plain text box on the full options page and in the userscript dialog, not in the toolbar popup (its sections are already tall, and the popup is for quick switches). It accepts `#rgb` and `#rrggbb`, with or without the `#`, in any case, shows the error as it is typed and stores lowercase `#rrggbb`. The setting is labelled "(experimental)" in every language. It colors every surface that carries the tag: the full badge, the compact badge, the chips of the Tag Kit section, the hover card entry's title and the banner's wash. Unset, a tag looks as it did, with the same violet and the same contrast. This lifts the AA and 3:1 guarantees of the Contrast section for the people who pick a color, and only for them. Nothing clamps, nudges or checks the color: the picked color is the one used, and the help text says that contrast is not checked. Rejected: clamping or auto-adjusting a pick to keep AA (it would change the color the person chose, and the right amount depends on art and pages we do not control); a warning that blocks a low-contrast pick (a refusal the person did not ask for, with no good threshold across the full badge's grounds); a native color picker (a browser dialog that differs everywhere and cannot be typed into or read back by a screen reader as a code); a free choice of every shade (seven tags times seven shades is a form nobody finishes). It extends decision 2 and the Color section's "Violet is ours": the hue is ours by default and the person's by choice, never ours to judge with, so Principle 1 (label the report, never judge it) still holds. It follows decision 12 and Principle 7: the color is one custom property per kind on the root element (`--sar-kind-color-<id>`), never a per-node style. The chips and entries carry `data-sar-kind`, one hand-listed rule per kind reads that kind's property, and the shades are `color-mix()` of it at fixed shares that put the violet scale's shape on any color (the color plays accent 400; the full badge text is 37% of it into white, the compact surface 22% into black, the wash stops 31% and 66% into black at 80%). Custom properties inherit into the banner's and the dialog's shadow roots, so a change applies live and a chip is not drawn again. A banner with one tag takes that tag's color for its wash, and a banner that lists several keeps the default violet. Text on the banner, the switches, buttons and focus rings keep their tokens. Forced colors still override the badges. The userscript dialog gets the fields through a form capability (`colors`) apart from the layout context, so it keeps the popup layout. Open question 18 asks for the real contrast of a few popular picks.
50. **A "Tag Kit tags for this product" section below the user-defined tags, instead of one AI chip under Publisher** (decided 2026-10-25). Supersedes decision 44 and amends decisions 29 and 35. The summary row held one AI chip. Next to a banner that lists three kinds it looked like a bug, since the other kinds were missing, and it sat off the page's tag grid: a violet chip in a box of label and value rows. The section goes right below Steam's "Popular user-defined tags for this product:" block, with a small muted heading and the chips shaped like that row (19px, 2px apart, wrapping). It lists one chip for every disclosed kind that is enabled, not ignored and has its badge switch on, in registry order, all of them and with no "+N" chip, so a game that declares only kernel anti-cheat gets a section too. With no such kind there is no section and no heading. It is a block of its own with its own heading and hue, so decision 29's reason against the tag row (it never wraps, Steam hides the tags that do not fit, a chip there reads as a player tag) does not apply. Each chip opens the hover card with its own kind and does nothing on click: the jump to the banner went with the row, because one link cannot stand for several kinds and a card over the click path was why the two never combined. The section follows `.popular_tags_ctn`; without it, the last `.dev_row`; without both, nothing. Rejected: keeping the row and adding chips to it (still off the tag grid, and it repeats the banner under Publisher); chips in the store's tag row (decision 29); a "+N" chip (the section wraps, and a hidden kind is a kind the player never sees); a chip click that jumps to the banner (the same chip already opens the card, which quotes the developer, and four chips would share one target).
51. **DLC follow their base game's ignore, derived from Valve's parent field, with no list** (decided 2026-10-25). Ignoring a game for a tag, or for all tags, also ignores its DLC for that tag everywhere: the DLC rows of the base game's own page, the banner, search, wishlist and sale pages, and the hover card. Example: with AI ignored on ARC Raiders, the DLC rows on its page ("ARC Raiders - Frozen Trail Collector Set" and the rest) lose their AI chip and keep PvP, since only AI was ignored. The relation comes from the data the extension already fetches: a DLC item in GetItems carries `related_items.parent_appid`, the base game's app ID (captured for app 5201760, a DLC of 1808500, in `tests/fixtures/getitems/dlc-parent.json`). It rides the existing batch of up to 50 IDs, so it costs no request. The schema reads it as an optional branded `AppId` that degrades to no parent when missing or malformed, the verdicts of an app carry it as `parent`, and the verdict cache stores it (`CACHE_SCHEMA` 3 discards the entries written without it). One predicate, `isIgnored(ignored, id, kind, parent)`, decides for every surface. The ignored games list stays keyed by the games the person ignored, so no DLC appears in it, "Stop ignoring" on the base game restores the DLC, ignoring a DLC itself still works, and a DLC page whose base game is ignored for a kind shows no banner entry and no note for it. Unknown parent (not fetched yet, the HTML fallback, an item without the field) behaves as before. One level only, which is what Valve sends; the same field also names the parent of other child items such as a demo, and they follow it too. Rejected: a stored list of DLC IDs (stale the day a DLC ships, and a seed list rule 1 bans); reading the DLC page's "Downloadable Content for" link (one more page request per unseen DLC, against rule 13); reading the parent from the base game's page rows (covers only that page, not search, wishlist or a DLC opened directly); a second ignore entry per DLC written when the person ignores the base game (it never reaches a DLC released later and would fill the list the person reads).
52. **A person can ignore a developer or a publisher, from the banner, apart by role** (decided 2026-10-25; ADR 0013). A game is ignored for a tag, or for all tags, when one of its developers is on the developer list or one of its publishers is on the publisher list for it. The two roles are two lists, in two storage keys (`v2:allow-developers`, `v2:allow-publishers`), because avoiding a publisher's catalog says nothing about the studios it signs. The data comes from the same GetItems request with `include_basic_info`, which adds a few bytes per item and no request. A creator is keyed by the clan ID when Steam sends one (`c:<id>`) and otherwise by its exact name (`n:<name>`), because live answers carry `creator_clan_account_id` for Valve and CD PROJEKT RED and omit it for Embark Studios. An entry matches any key of the creator, so a name-keyed entry keeps working after Steam adds an ID. The control is a closed `details` under "Ignore this game", titled "Ignore a developer or publisher", with one row per name and role (a company that develops and publishes appears twice) and, on each row, a link-style button per tag the banner lists and one for all tags. The section forgets its state on reload, like the banner (decision 13), and keeps it across a redraw. A tag silenced through a creator becomes a note with Undo, in the words "Ignored for games by Valve (Developer): Uses Kernel Level Anti-Cheat", and a creator ignored for all tags leaves one note. Settings lists the two lists in two cards after "Games you ignored", grouped by scope, each with "Stop ignoring"; the popup hides an empty card. The same predicate decides everywhere (`isIgnored`), so chips, the hover card, the list filter and the tag section follow with no edit of their own. Known risks: two companies with one name share an entry, a renamed studio stops matching an entry made by its old name, and a large publisher hides many games, which is the request. Rejected: one list for both roles (merges two decisions); the name only (collides and breaks on rename for creators that do have an ID); the clan ID only (no control for Embark Studios and others); reading creator IDs from the DOM (only classic rows carry them, and each surface would need its own code).

52. **A one-line count of what Hide removed, above search results, with a reveal for this page only** (decided 2026-10-25). With a tag's list filter on Hide, results leave the list without a trace, and the setting lives in the popup. When at least one result in the current list is hidden, one line right before the store's result rows reads "Tag Kit hid 3 results." with a "Show them" button; after a click it reads "Tag Kit is showing 3 hidden results." and "Hide them". The line names a number only, never a tag or a verdict (principle 1). It takes the banner's ignored-note geometry in neutral, with the note background, the muted 12px type and the in-bubble underlined link as its button, because it reports what the extension did and not a tag. The reveal is one root attribute, `data-sar-reveal`, which the hide rules skip and the dim rules match, so the shown results come back dimmed, as a host that cannot hide does, and stay recognizable. Nothing is stored: a reload, a new list from the store, `pagehide` or the count reaching zero ends the reveal. The count is one `querySelectorAll` over the list for the hosts whose `data-sar-kinds` holds a kind the root's filters hide, run in one animation frame after a mutation that can change it (a `data-sar-kinds` write, a root filter write, a marked host leaving). It follows infinite scroll, settings, the ignore list and new verdicts without a scan pass or polling. A polite live region repeats the line once it has held for one second. Search comes first; another list surface is one `LIST_PLACEMENTS` entry. Library check: nothing adopted. `Intl.PluralRules` through the catalog's `plural`, the shared `announce` helper and one `MutationObserver` cover it, while announcer packages such as `@react-aria/live-announcer` assume React or add a second global live region. Rejected: a checkbox in the store's search sidebar (it couples to that markup and needs more copy; it can follow), a count per tag (it would name tags as facts in a line about hiding), a reveal without the dim (the shown results would look like every other row), and a stored reveal (it would quietly undo the person's Hide on every page).

## Ideas credited

Nothing was copied from prior-art extensions. Ideas that shaped this, to credit in the project README: a dismissible banner in the style of the store's DRM notice instead of a modal (requested in Augmented Steam issue 1913, shipped by Obvious Steam AI); dim or hide modes for lists (AI warning for Steam); falling back from hiding to highlighting where a list cannot hide (AI Generated Content Filter for Steam); a control for the list filter where people browse, shown by the search sidebar toggles of AI warning for Steam and Steam AI Games Indicator and requested in AI warning for Steam issue 8 (the hidden results notice, decision 52); a block of our own in the summary box (SteamDB's browser extension adds its rating row there).

## Open questions

1. **Wishlist anchor.** The wishlist is React and the sampled one was private; the full badge's exact anchor is unverified.
2. **Row hover color.** `#2a475e` is assumed. The badge passes on it (5.21:1), but confirm the live value.
3. **CSP for styles.** The banner and dialog use `adoptedStyleSheets`; badges rely on the content stylesheet or `GM_addStyle`. If the store's CSP blocks either, fall back to light DOM plus the badge reset.
4. **Line clamp with `pre-line` in Firefox.** Unchecked with notes that contain blank lines.
5. **Forced colors.** The rules are written but unchecked in Windows high contrast mode.
6. **"Steam" in the name, the description and the icon.** "Tag Kit for Steam" and `ext_description` use the trademark descriptively, and the extension icon holds the Steam glyph (decision 40), shown in the README logo, the store listing images and the settings headers too; check all of them against the listing policies.
7. **Language of the quoted notes.** The API does not say which language the developer wrote in, so the quote carries no `lang`.
8. **Dim distinctness.** 0.4 against the store's 0.3 is a small difference. If people confuse the two, profile a cheap second cue (a tinted outline on the host) on a sale page first.
9. **Banner next to the DLC bubble.** A game with DLC can carry a report too, so our banner may stack with the store's plum DLC bubble. Compare the two side by side on such a page.
10. **Compact badge and the store's flags.** Both share the 5px row, and the compact badge carries the full label (decision 35). On a 184px capsule the English label leaves 33px beside a 64px flag and the Spanish one 9px; a longer translation can reach a store flag at the other corner. Measure the widest flag and cap our label if needed.
11. **Banner button hover.** The 10% white hover wash is ours; the store's white-transparent hover state was not sampled.
12. **Restore: merge or replace.** Restore merges game lists by default. Decide whether to also offer "replace everything", for someone who wants this browser to match the backup exactly.
13. **History in backups.** Lookup history is the bulk of the file and refreshes itself anyway. Decide whether it stays in, becomes optional, and how large a file to accept.
14. **Tag section over background art.** The tag block sits on transparent layers: a column gradient (to the right, from 0 to 40% black) and the page's glow, over the game's background art when the page has some. Contrast is measured on the plain page color. On a page with custom art, measure the chips and the heading against the lightest pixel behind the block.
15. **Tag section in the narrow layout.** The store's responsive layout moves the summary box. Confirm the section still follows the tags block there.
16. **Anchor classes and heading style.** `.popular_tags_ctn` and `.dev_row` are the store's class names as known, and no captured fixture holds the summary box (the fixtures keep the description column only). Capture one page with user tags and one without, add them to `tests/fixtures/app-page/`, and sample the heading's size, color and spacing, which `tokens.css` approximates with the tag font and `sar-color-text-muted`. A game with two review rows and a publisher name that wraps makes the box taller; check that the section does not hang past the media's bottom edge.
17. **Hand-hinted 16px and 32px marks.** The interim renders are weak at 1x toolbar size, so hinted files are needed before store submission. Drop them in as `assets/icons/icon-16.svg` and `icon-32.svg`; `mise run icons` then renders from them. Fallback: a simplified 16px mark with ring and tag only, and cuts of at least 1px.
18. **Custom colors and contrast.** The color is used as given (decision 49). Measure the full badge, compact badge and banner for a few popular picks (pure red, yellow, white, black, a pastel) on the store grounds, and decide whether the help text should name the risk more plainly or whether the shares in `sar-kind-mix-*` need tuning.
19. **Banner with several tags.** The wash keeps the default violet while the color setting is experimental. A wash that blends the colors of its entries is the option to try later.
20. **Hidden results notice on the live search page.** It sits right before `#search_resultsRows`, under the store's sort bar, which the captured fixture does not hold. Check it on a live page in both languages, next to any line the store shows about results its own preferences leave out, and when the store loads a new search without a reload.
21. **Dim on reveal.** Shown results come back dimmed (decision 52). If people expect them at full strength, drop the dim rules for `data-sar-reveal`; the line still tells the state.
