# RQ1: How do large open-source browser extensions (and their userscript variants) version, build, publish and host releases?

Research date: 2026-10-20. All GitHub API data below was read on that date and will drift. Page contents were read through a summarising fetch tool unless a source says "verbatim"; re-fetch before quoting.

## Answer in short

- Of the projects read, only Refined GitHub publishes to stores from CI (daily calver tag, `chrome-webstore-upload-cli@3`, `web-ext sign --channel listed`, secrets in GitHub environments `Chrome` and `Firefox`, draft GitHub release). uBlock Origin, Dark Reader, Augmented Steam, SteamDB and Return YouTube Dislike only build and attach artifacts in CI; store upload is outside the repo (unverified who or how). Bitwarden bumps versions by workflow plus PR and keeps a separate `chrome-beta` build, but its build workflow publishes nothing.
- Nobody uses changelog fragments: uBO and Dark Reader hand-edit `CHANGELOG.md`; Refined GitHub uses GitHub auto-generated notes on a draft release that a human curates.
- Store version rules reshape a calver train: 1 to 4 dotted integers, no leading zeros (`2026.10.05` is invalid, `2026.10.5` is valid), each integer 0..65535 for Chrome; `2026.10.20` and `2026.10.20.1` are valid in both stores. AMO never lets a version number be reused, and the CWS needs each upload to out-rank the previous one.
- No keyless/oidc auth was found for the Chrome Web Store, AMO or Edge. CWS API v2 (launched 2025-10-15) adds service accounts, staged publish and deploy percentage; v1.1 was announced to be supported only until 2026-10-15, which is past.
- Node 24 still ships corepack (experimental); node 25 and later do not. AMO's default reviewer environment names node 24.14.0, where `corepack enable` is valid, but the readme should pin a fallback.

## Findings

### uBlock Origin (gorhill/uBlock)

Version scheme and bump. The version lives in a plain text file `dist/version` (content at fetch time `1.75.1.16`) (source: https://raw.githubusercontent.com/gorhill/uBlock/master/dist/version). `tools/make-firefox-meta.py` reads it and writes it unchanged into the Firefox manifest (source: https://raw.githubusercontent.com/gorhill/uBlock/master/tools/make-firefox-meta.py). The repo copy of `platform/firefox/manifest.json` carries a placeholder `1.9.15.101`; the committed manifest is not the shipped one (source: https://raw.githubusercontent.com/gorhill/uBlock/master/platform/firefox/manifest.json). Dev builds use a different spelling in git: the same build is tagged `1.75.1b16` (prerelease) while the manifest says `1.75.1.16`; stable tags are plain `1.75.0`, `1.74.0` (source: https://api.github.com/repos/gorhill/uBlock/releases?per_page=8). Precedent: git tag spelling and manifest spelling may differ. Nothing in CI checks the `b16` to `.16` mapping (unverified; it looks like a manual convention).

Changelog. Hand-maintained `CHANGELOG.md`; the workflow copies its top section (up to the first `----------` line) into the release body and prepends `.github/workflows/RELEASE.HEAD.md`, a template with a `%version%` placeholder holding the "install the developer build" text (source: https://raw.githubusercontent.com/gorhill/uBlock/master/.github/workflows/main.yml, https://raw.githubusercontent.com/gorhill/uBlock/master/.github/workflows/RELEASE.HEAD.md).

Workflow and store publishing. `.github/workflows/main.yml` is the only workflow besides the template. It fires on `create`, gated by `startsWith(github.ref, 'refs/tags/')`; the job (permissions `contents: write`) runs `tools/pull-assets.sh`, takes `VERSION` from the tag name, runs `tools/make-chromium.sh` and `tools/make-firefox.sh` with it, then `gh release create ... --prerelease --draft --notes-file release.body.txt` uploading `uBlock0_<v>.chromium.zip` and `uBlock0_<v>.firefox.xpi` (source: main.yml URL above). `--prerelease --draft` is hard-coded and a human publishes. The only secret is the built-in `GITHUB_TOKEN`. There is no store upload step; stable store submissions are therefore done outside CI (unverified: no document found saying how). `make-chromium.sh` has a comment `# Chrome store-specific` before copying the `nb` locale to `no`; the zip is shaped for the CWS (source: https://raw.githubusercontent.com/gorhill/uBlock/master/tools/make-chromium.sh).

Dev channel as self-hosted signed XPI. Prerelease tags `1.75.1b11` to `1.75.1b16` (2026-10-11 to 2026-10-19) each carry `uBlock0_<v>.chromium.crx`, `.chromium.zip` and `.firefox.signed.xpi` (source: https://api.github.com/repos/gorhill/uBlock/releases?per_page=8). `dist/firefox/updates.json` is an add-on update manifest keyed by the ID `uBlock0@raymondhill.net` whose `update_link` points at the GitHub release asset `.../releases/download/<tag>/uBlock0_<v>.firefox.signed.xpi`, `strict_min_version` 115.0 (source: https://raw.githubusercontent.com/gorhill/uBlock/master/dist/firefox/updates.json). The `.signed.xpi` is produced outside the CI workflow (signed by hand, presumably through the AMO unlisted channel; unverified). The file shows that Mozilla's self-hosted update model (see store constraints) works with GitHub release assets as `update_link`. `dist/README.md` says users of github-hosted builds update manually and that the Firefox beta is a separate signed file (source: https://raw.githubusercontent.com/gorhill/uBlock/master/dist/README.md).

AMO source. The MV2 build only copies files (`tools/make-*.sh`) and has no bundler visible in the tools list (source: https://api.github.com/repos/gorhill/uBlock/contents/tools); the package is its own source (inference, unverified as stated policy).

### Dark Reader (darkreader/darkreader)

Version scheme and bump. Plain semver, tags `vX.Y.Z` (`v4.9.133`). The maintainer pushes a commit whose message is the bare version (`4.9.133`); that commit touched exactly `CHANGELOG.md` (+5 lines), `package.json`, `package-lock.json` and `src/manifest.json` (source: https://api.github.com/repos/darkreader/darkreader/commits/v4.9.133). The manifest version is not derived from package.json: `tasks/bundle-manifest.js` reads `src/manifest.json` and merges per-platform patches; both files are bumped by hand; debug builds force `version = '1'` (source: https://raw.githubusercontent.com/darkreader/darkreader/main/tasks/bundle-manifest.js). Cadence in 2026: v4.9.128 on 06-19, .129 on 07-14, .130 on 09-01, .131 on 09-14, .132 on 09-15, .133 on 09-24 (source: https://api.github.com/repos/darkreader/darkreader/releases?per_page=6). CONTRIBUTING forbids contributors from changing `package.json`, `package-lock.json` and the build process, consistent with a maintainer-only release commit (source: https://raw.githubusercontent.com/darkreader/darkreader/main/CONTRIBUTING.md).

Changelog. Hand-written `CHANGELOG.md`, newest first, a heading with date per release and terse bullets, often prefixed with browser names (source: https://raw.githubusercontent.com/darkreader/darkreader/main/CHANGELOG.md). It is also uploaded as a release asset (source: https://raw.githubusercontent.com/darkreader/darkreader/main/.github/workflows/tagged-release.yml).

Workflow. `.github/workflows/` has `tagged-release.yml`, `test-browser.yml`, `test-code.yml`, `test.yml` (source: https://api.github.com/repos/darkreader/darkreader/contents/.github/workflows). `tagged-release.yml` ("Create binary for release") triggers on tag push `v*` and on `workflow_dispatch` (inputs `retention_days`, `node_version`, default `22.x`); one job: `npm ci`, `npm run release`, then `softprops/action-gh-release@v2` only on tag refs, attaching `build/release/darkreader-*` and `CHANGELOG.md`; non-tag runs only upload an artifact (source: tagged-release.yml URL above). No secrets beyond the default token. `npm run release` is `npm test && npm run lint && node tasks/cli.js build --release` (source: https://raw.githubusercontent.com/darkreader/darkreader/main/package.json). V4.9.133 assets: `CHANGELOG.md`, `darkreader-chrome-mv3.zip`, `darkreader-chrome.zip`, `darkreader-firefox.xpi`, `darkreader-thunderbird.xpi` (source: releases API above).

Store publishing and beta. No store step in any workflow; stores are published outside the repo (unverified: no document states who or how). No prerelease channel in the last six releases. A commit "Edge MV3 build" (2026-09-11) shows per-store build targets being added (source: https://api.github.com/repos/darkreader/darkreader/commits?per_page=8&path=package.json).

AMO store signatures kept in git. `integrity/firefox/<version>/` holds Mozilla's `mozilla.rsa`, `cose.sig` and `mozilla-recommendation.json` per published version; `tasks/bundle-signature.js` generates `META-INF/manifest.mf`, `mozilla.sf` and `cose.manifest` and copies the stored files; `npm run build -- --firefox --version=4.9.63` then rebuilds the store-signed archive. The readme calls it experimental and says only Firefox signatures are present (sources: https://raw.githubusercontent.com/darkreader/darkreader/main/tasks/bundle-signature.js, https://raw.githubusercontent.com/darkreader/darkreader/main/README.md). This is the only reproducible-build proof scheme found.

### Refined GitHub (refined-github/refined-github)

Workflows: `actionlint.yml`, `conversation.yml`, `daily.js`, `daily.yml`, `hotfixes.yml`, `pr.js`, `pr.yml`, `relative-ci.yml`, `release.yml`, `test.yml` (source: https://api.github.com/repos/refined-github/refined-github/contents/.github/workflows).

Version and release. `release.yml` was read verbatim. It is generated from `fregante/ghatemplates/webext` and has `workflow_dispatch` only, with an optional `manual-version` input ("leave empty for daily version"); the generator option `exclude on.schedule` is recorded in the header, which means no cron trigger in this file (the reason and what `daily.yml` does were not read; unverified). Job `Version`: checkout, setup-node from `package.json`, `npm ci`, `npm run build`, `fregante/daily-version-action@v3.1.0` (creates a calver tag only if HEAD has no tag; outputs `created` and `version`; `custom-version` overrides), then `yq -i '.version = strenv(DAILY_VERSION)' distribution/manifest.json` (the repo never holds the bumped version), uploads `distribution` as an artifact, zips it and runs `gh release create "$DAILY_VERSION" "$FILENAME" --draft --generate-notes` (comment: "Create as draft to curate it before sending it out") (source: https://raw.githubusercontent.com/refined-github/refined-github/main/.github/workflows/release.yml, verbatim). The action readme shows a `v20.12.31` style example (two-digit year) and does not document same-day recuts (source: https://raw.githubusercontent.com/fregante/daily-version-action/main/readme.md); how the same-day case is named is unverified.

Store jobs. `Chrome` (needs `Version`, `environment: Chrome`): `npx chrome-webstore-upload-cli@3` with `EXTENSION_ID`, `CLIENT_ID`, `CLIENT_SECRET`, `REFRESH_TOKEN`. `Firefox` (`environment: Firefox`): writes `/tmp/amo-metadata.json` with `{"version":{"release_notes":{"en-US":"<github release url>"}}}` and runs `npx web-ext@9 sign --channel listed --amo-metadata /tmp/amo-metadata.json` with `WEB_EXT_API_KEY` and `WEB_EXT_API_SECRET` (source: release.yml above). Actions are pinned by commit sha with version comments. Secrets live in GitHub environments, which can carry required reviewers (a general GitHub feature that this repo's files did not show; unverified here).

Caveat on the Chrome job. The pinned `chrome-webstore-upload-cli@3` predates the CWS API v2: v4.0.0 (2026-05-12) switched to API v2 and made `PUBLISHER_ID` mandatory, and the workflow does not set it (source: https://api.github.com/repos/fregante/chrome-webstore-upload-cli/releases?per_page=5). CWS announced v1.1 support only until 2026-10-15 (see store constraints); this job may now be broken (unverified; not tested).

Changelog and beta. None authored: release notes are GitHub's auto-generated notes on a draft that a maintainer curates; the AMO release notes field is only a link to the GitHub release. No beta channel.

AMO source. The Firefox step is named "Upload build and source code" but its command has no `--upload-source-code` flag; release.yml as read does not upload source (unverified how source is handled; the build config was not read).

### Bitwarden browser (bitwarden/clients)

Version and bump. `apps/browser/package.json` version is `2026.10.1` (calver `YYYY.M.patch`, month unpadded) (source: https://raw.githubusercontent.com/bitwarden/clients/main/apps/browser/package.json); the latest desktop tag seen is `desktop-v2026.10.0` (2026-10-15); tags carry a per-client prefix (source: https://api.github.com/repos/bitwarden/clients/releases?per_page=6; browser tags not seen in the part read, unverified). `repository-management.yml` (workflow_dispatch) takes `task` ("Version Bump" or "Version Bump and Cut rc"), booleans `bump_browser`, `bump_cli`, `bump_desktop`, `bump_web`, an optional `version_number_override`, else the next version comes from `bitwarden/gh-actions/version-next@main`. It runs `npm version --workspace=@bitwarden/browser` for `apps/browser/package.json`, uses `bitwarden/gh-actions/version-bump@main` for `apps/browser/src/manifest.json` and `manifest.v3.json`, commits "Bumped client version(s)" on a branch `version-bump-<timestamp>`, opens a PR "Bump client version(s)" labelled "version update", and for the rc task creates an `rc` branch; it creates no tag (source: https://raw.githubusercontent.com/bitwarden/clients/main/.github/workflows/repository-management.yml). Closest prior art to "bot opens a version PR".

Build and publish. `build-browser.yml` runs on PR and on push to `main`, `rc`, `hotfix-rc-browser`, plus dispatch. Build number is the short sha; Node comes from `.nvmrc`; a matrix builds `chrome`, `chrome-beta`, `edge`, `firefox`, `firefox-mv3` (artifact named `DO-NOT-USE-FOR-PROD-dist-firefox-MV3`) and `opera-mv3`; Safari builds on macOS only when secrets exist. It publishes nothing and creates no GitHub release (source: https://raw.githubusercontent.com/bitwarden/clients/main/.github/workflows/build-browser.yml). Store submission is outside this workflow (unverified where).

Beta channel as a separate CWS listing. The `chrome-beta` entry stamps a beta ordinal read from `apps/browser/beta-release.json` (`{"betaNumber": 1}`) via `update:beta:chrome`, which runs `scripts/update-manifest-beta.sh` (script body not readable; 404 at the guessed path), with the workflow comment "The Chrome Web Store rejects an upload that does not out-rank the previous one in the same listing" (sources: build-browser.yml above, https://raw.githubusercontent.com/bitwarden/clients/main/apps/browser/beta-release.json, https://raw.githubusercontent.com/bitwarden/clients/main/apps/browser/package.json). A separate listing gives a separate version namespace for betas. Google's own guidance for betas: publish a second item, private, unlisted or public, with "BETA" or "DEVELOPMENT BUILD" in the name and a description that says it is a beta, otherwise both items may be taken down (source: https://developer.chrome.com/docs/webstore/cws-dashboard-distribution).

AMO source for reviewers. The `build-source` job produces `browser-source-<build>.zip` ("Build sources for reviewers") for both the open-source and commercial variants; the Firefox job fails builds containing files over 5MB (source: build-browser.yml above). The only prior art found that produces a dedicated reviewer source zip in CI.

Versions are decoupled: the extension is `4.1.0` in `package.json` (packageManager `npm@10.8.2`) and the userscript is `3.2.1` in `Extensions/UserScript/userscript-version.json` (sources: https://raw.githubusercontent.com/Anarios/return-youtube-dislike/main/package.json, https://raw.githubusercontent.com/Anarios/return-youtube-dislike/main/Extensions/UserScript/userscript-version.json). The userscript config (`userscript.meta.js`, a webpack-userscript style config module) sets both `updateURL` and `downloadURL` to `https://github.com/Anarios/return-youtube-dislike/raw/main/Extensions/UserScript/Return%20Youtube%20Dislike.user.js`, i.e. the committed file on `main`; no release asset is involved (source: https://raw.githubusercontent.com/Anarios/return-youtube-dislike/main/Extensions/UserScript/userscript.meta.js). How the extension reaches stores is not in the repo workflows (unverified).

### Store constraints: version format

Chrome: `version` is one to four dot-separated integers, each 0 to 65535, a non-zero integer cannot start with zero (`032` is invalid), the version cannot be all zeros, missing segments count as zero; `version_name` is a free display string such as `1.0 beta` (source: https://developer.chrome.com/docs/extensions/reference/manifest/version). firefox/amo: one to four numbers, no leading zero on non-zero numbers, `version_name` is separate; AMO allows up to 9 digits per number, regex `^(0|[1-9][0-9]{0,8})([.](0|[1-9][0-9]{0,8})){0,3}$`, and Firefox 108+ warns on non-matching versions (source: https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/version; the regex is single-source). Consequence for the train: `2026.10.20` (three segments) and `2026.10.20.1` (four, the maximum) are valid in both browsers; zero-padded forms such as `2026.10.05` or `2026.10.20.01` are invalid in both; the manifest version must be the unpadded form while the git tag may stay padded (same two sources; the Chrome docs give the leading-zero rule, the MDN page states it for both). A fifth segment is impossible; there is no room for a channel or build-id segment beyond `.NN`.

Monotonic and unique numbers. Chrome requires each new version number to be larger than the previous (source: https://developer.chrome.com/docs/webstore/update, page dated 2020-12-03, possibly stale) and Bitwarden's workflow comment states the same for the CWS (source: build-browser.yml above). AMO never lets a version number be reused, even after the version is deleted or disabled, in either channel (sources: Mozilla blog "AMO updates on version number re-use" as summarised by a search tool, plus forum threads about "Version already exists"; the blog URL itself returned 404 when fetched directly; this is lightly verified); the AMO API states a rollback version string "must be unique across all channels" (source: https://mozilla.github.io/addons-server/topics/api/addons.html). Edge: bump the manifest version when the package changes (source: https://learn.microsoft.com/en-us/microsoft-edge/extensions/update/api/using-addons-api, general guidance, secondary).

### Store constraints: review latency and cadence

CWS: most items are reviewed "within a few days", can take "up to a few weeks"; pending more than three weeks means contact support. Closer scrutiny for new developers, new items, dangerous permissions, significant code changes and broad host permissions such as `<all_urls>`; obfuscation is disallowed, minification is allowed but can slow review; updates and new items use the same process (source: https://developer.chrome.com/docs/webstore/review-process). The page does not say frequent submissions are discouraged and does not document a limit on pending submissions; the v2 `cancelSubmission` method cancels "the current active submission", implying one active submission per item (sources: review-process URL, https://developer.chrome.com/docs/webstore/api/reference/rest/v2/publishers.items/cancelSubmission). After approval a staged item can be published within 30 days or it reverts to draft (source: https://developer.chrome.com/docs/webstore/publish). New publishers are limited to two published extensions at first (same source).

AMO: automated validation first; "up to 24 hours" to be signed and published for listed, longer if manual review is selected; unlisted gets the same validation and signing, and manual review can happen any time after (source: https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/). No AMO or CWS page read discourages daily submissions; the practical limits are review load, the unique-version rule, and that "significant code changes" raise CWS scrutiny. Observed cadence of big projects: Dark Reader at most a few releases per month (releases API above), uBO dev builds almost daily on GitHub only, Refined GitHub's design is daily (daily-version-action) but its workflow has no schedule trigger.

### Store constraints: Chrome Web Store API in 2026

V2 launched 2025-10-15; the announcement says v1.1 would be supported "until 15th October 2026" (source: https://developer.chrome.com/blog/cws-api-v2; a translated copy surfaced by search carries the same date). That date has passed as of 2026-10-20 and no post-deadline notice was found (unverified whether v1.1 still answers). V2 adds service accounts, percentage rollout without review, cancel pending submission, `STAGED_PUBLISH`; it cannot create items and cannot change visibility (same blog). Methods: `media.upload`, `publishers.items.publish`, `fetchStatus`, `cancelSubmission`, `setPublishedDeployPercentage` (source: https://developer.chrome.com/docs/webstore/api). `POST https://chromewebstore.googleapis.com/v2/publishers/{publisherId}/items/{itemId}:publish` takes `publishType` (`DEFAULT_PUBLISH` or `STAGED_PUBLISH`), `deployInfos[].deployPercentage` (0 to 100), `skipReview` (only if the item qualifies) and `blockOnWarnings`; scope `https://www.googleapis.com/auth/chromewebstore` (source: https://developer.chrome.com/docs/webstore/api/reference/rest/v2/publishers.items/publish). `setPublishedDeployPercentage` raises the percentage of the published revision without review, only for items with more than 10,000 seven-day active users, and the value "must be larger than the existing target percentage" (sources: https://developer.chrome.com/docs/webstore/api/reference/rest/v2/publishers.items/setPublishedDeployPercentage, https://developer.chrome.com/docs/webstore/update). Publishing a new version during a rollout stops the old one from reaching more users, and a version following a taken-down or warned one must go to 100% (update page). A small extension below 10,000 users cannot use partial rollout.

Auth. Two models: (a) OAuth client ID, client secret and refresh token (what `chrome-webstore-upload-cli` v4 and Refined GitHub use; v4 also needs `PUBLISHER_ID`; flag `--deploy-percentage` defaults to 100; running with no command uploads and publishes) (sources: https://raw.githubusercontent.com/fregante/chrome-webstore-upload-cli/main/readme.md, https://api.github.com/repos/fregante/chrome-webstore-upload-cli/releases?per_page=5); (b) a Google cloud service account whose email is added in the developer dashboard, one per publisher, with a token obtained by gcloud impersonation (needs `roles/iam.serviceAccountTokenCreator`) or by a JSON key exchanged for a JWT (page warns key files are a risk) (source: https://developer.chrome.com/docs/webstore/service-accounts). Trusted testers are an account-level list (separate lists need separate accounts) plus per-item Google groups; private, unlisted and public visibility all pass the same review (source: https://developer.chrome.com/docs/webstore/cws-dashboard-distribution). The CLI's `--trusted-testers` flag was removed in v4.0.2 as non-functional (releases API above).

### Store constraints: AMO API, channels, source

Auth: API key and secret from the AMO developer hub; each request carries `Authorization: JWT <token>`, HS256 signed with the secret, claims `iss` (the key), `jti`, `iat`, `exp` with `exp` at most five minutes after `iat` (source: https://mozilla.github.io/addons-server/topics/api/auth.html). `web-ext sign` reads `WEB_EXT_API_KEY` and `WEB_EXT_API_SECRET`; `--channel listed|unlisted`; `--amo-metadata` is required for the first listed version (`categories`, `summary`, `license`) and may carry `approval_notes` and release notes later; `--approval-timeout` defaults to 15 minutes (0 disables the wait); `--upload-source-code` exists (description cut off in the page read); `--use-submission-api` was removed in web-ext 8 (source: https://extensionworkshop.com/documentation/develop/web-ext-command-reference/). `web-ext sign` v8+ handles initial and update submissions for both channels; the signing API v4 is updates-only for listed (source: https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/). API v5 version create: `POST /api/v5/addons/addon/{id}/versions/` takes the upload uuid; the channel (`listed`, `unlisted`, `enterprise`) is set on the upload; `source` must be sent as multipart form-data, never JSON; `approval_notes` is private to reviewers (source: https://mozilla.github.io/addons-server/topics/api/addons.html).

Unlisted vs listed. Both are signed through AMO; unlisted cannot be viewed or installed from AMO and is for self-distribution or betas; listed auto-updates "each time a new version is listed on AMO" (source: signing-and-distribution-overview URL). Self-hosted updates: set `browser_specific_settings.gecko.update_url` to an HTTPS `updates.json` (`addons.<id>.updates[]` with `version`, `update_link`, optional `update_hash`, `applications.gecko`); `update_link` must be HTTPS unless `update_hash` is given; Firefox checks every 86400 seconds by default and installed copies keep the `update_url` of the installed version (source: https://extensionworkshop.com/documentation/manage/updating-your-extension/). UBO's `dist/firefox/updates.json` is a live instance of this.

Source submission. Required when the package was produced with minifiers, bundlers, template engines or custom pre-processing; reviewers re-run the instructions and diff the output, "there must be no differences"; give a readme with OS, tool versions, full commands and the lockfile; build tools must be open source and run locally; the default reviewer environment when none is stated is Ubuntu 24.04.4 LTS, ARM64, 10GB RAM, 6 vCPU, Node 24.14.0, npm 11.9.0; max source size 200MB; the documented upload path is the developer hub web UI (Manage Status & Versions, then the version, then Source code), and the page advises against minifying (source: https://extensionworkshop.com/documentation/publish/source-code-submission/). API upload is the v5 multipart `source` field above.

### Store constraints: Edge Add-ons API

Update API only: no endpoint creates a product or edits listing metadata; the first publish and metadata changes happen in Partner Center. v1.1 uses an API key plus client ID sent as `Authorization: ApiKey <key>` and `X-ClientID: <id>`; Partner Center shows an expiry date for each API key. Endpoints under `https://api.addons.microsoftedge.microsoft.com`: `POST /v1/products/$productID/submissions/draft/package` (zip body, 202 with a `Location` operation ID), `GET .../draft/package/operations/$operationID`, `POST /v1/products/$productID/submissions` (publish, body with notes), `GET .../submissions/operations/$operationID`. The page says v1 (client secret and bearer token) support ends 2024-12-31 and was last updated 2026-09-02 (source: https://learn.microsoft.com/en-us/microsoft-edge/extensions/update/api/using-addons-api). Augmented Steam and Dark Reader both build Edge targets (sources above), and Dark Reader added an Edge MV3 build in 2026-09.

### Store constraints: OIDC and keyless auth

None found for any of the three stores. CWS docs describe OAuth refresh tokens, impersonation and JSON keys, and do not mention workload identity federation (source: https://developer.chrome.com/docs/webstore/service-accounts); searches for AMO oidc/trusted publishing and for CWS workload identity federation returned nothing (sources: web searches run 2026-10-20, negative results, treat as unverified); AMO uses JWT API keys (auth page above); Edge uses expiring API keys (Edge page above). Google workload identity federation could in principle mint a short-lived access token for the linked service account from a GitHub OIDC token, avoiding a JSON key; no source shows the CWS accepting it (unverified, would need a test). Contrast: PyPI trusted publishing has no counterpart in any of the three stores. No third-party tool was found that provides keyless store publishing.

### Userscript hosting

`@updateURL` and `@downloadURL`. Violentmonkey: `@downloadURL` is checked for updates at a regular interval and on user request, it is added automatically with "install from URL", a script with no `@version` is never updated automatically, `@version` parts are dot-joined and must start with numbers (source: https://violentmonkey.github.io/api/metadata-block/). The Tampermonkey documentation page returned only a table of contents; tampermonkey-specific rules (check interval, meta-only check via `.meta.js`) are unverified (source attempted: https://www.tampermonkey.net/documentation.php). The fetched Violentmonkey page does not state whether the installed version is compared with a higher `@version` (unverified; in practice a bumped `@version` is needed).

GitHub release assets. The stable link form is `https://github.com/<owner>/<repo>/releases/latest/download/<asset-name>` (source: https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases). "Latest" is the most recent non-prerelease, non-draft release ordered by `created_at`, where `created_at` is the date of the commit used for the release (source: https://docs.github.com/en/rest/releases/releases). Consequences: a prerelease nightly never moves `releases/latest`, a draft never does, and the asset file name must stay constant across releases for the URL to keep working (the constant-name requirement is an inference). Two other hosting patterns seen: uBO uses `releases/download/<tag>/<asset>` links inside a JSON update manifest (updates.json above); Return YouTube Dislike uses `raw/main/...user.js` committed to the default branch.

Greasy Fork. The API help page says Greasy Fork can check for updates from push and release webhook notifications from GitHub, gitlab and bitbucket (source: https://greasyfork.org/en/help/api); the dedicated webhook page returned 503 and the sign-in page; the payload URL, secret and event setup are unverified. A 2017 feedback-forum post says webhook events fetch code from git rather than over HTTP, removing a 5 minute GitHub cache delay (source: search result for https://greasyfork.org/en/forum/discussion/comment/33075/, secondary and old). Whether the sync URL can be a `releases/latest/download/...` redirect is unverified.

Greasy Fork rules (source: https://greasyfork.org/en/help/code-rules): code "must not be obfuscated or minified"; bundled code (the page mentions webpack) must keep whitespace and variable names; minifying to fit the 2 MB limit is disallowed; libraries should use `@require` unless there is a technical reason, and inline libraries must name their source; the primary functionality must be in the posted code (scripts that mainly load core code from elsewhere are disallowed); alternate download URLs meant to replace the Greasy Fork version and update checks more than once per day are disallowed. Rewriting: Greasy Fork adds or updates `@updateURL` and `@downloadURL` to point to itself and removes `@installURL` (source: https://greasyfork.org/en/help/rewriting); the meta-keys page says it strips these keys to keep a script installed from Greasy Fork updating only from Greasy Fork, requires `@version`, and warns when it is decremented or not incremented after a code change (source: https://greasyfork.org/en/help/meta-keys). One source file can therefore carry GitHub update URLs for GitHub installs while the Greasy Fork copy is rewritten. Its own moderation or review beyond these rules was not read (unverified).

Keeping extension and userscript in sync. One example found, Return YouTube Dislike: separate version numbers, one repo, CI builds both and fails if the committed userscript differs from a fresh build (sections above). No project found that derives both versions from one release tag; a search for such repos returned only a vue userscript template using a `@require` loader (low-trust search result, unverified).

### Node and corepack

Node 24 still ships corepack. The node v24 docs say "corepack will no longer be distributed starting with Node.js v25", marked stability 1 (experimental), and point to the userland module (source: https://nodejs.org/docs/latest-v24.x/api/corepack.html). The corepack readme says it is distributed with node "from version 14.19.0 up to (but not including) 25.0.0" and gives `npm install -g corepack` as the manual route (source: https://raw.githubusercontent.com/nodejs/corepack/main/README.md). The v24 changelog shows node 24.21.0 (2026-09-08) with "deps: update corepack to 0.36.0" and 24.22.0 as the newest lts "Krypton" at fetch time (source: https://raw.githubusercontent.com/nodejs/node/main/doc/changelogs/CHANGELOG_V24.md). Node 25.0.0 lists "build: stop distributing corepack" (#57617) and "build: remove corepack from release tarballs" (#59835) (source: https://nodejs.org/en/blog/release/v25.0.0). A search summary dates the tsc decision 2025-03-19 (secondary, unverified).

For AMO reviewers: the default reviewer environment names node 24.14.0 and npm 11.9.0 on Ubuntu 24.04.4 (source: source-code-submission page above); `corepack enable` then `pnpm install` should work if reviewers use the official node build; whether a distro-packaged node includes corepack is unverified. The readme should therefore (a) state the node version explicitly, (b) say `corepack enable` is valid on node 24 and earlier, and (c) give `npm install -g corepack` as the fallback for node 25+. The `packageManager` field with a sha hash is "strongly recommended" by the corepack readme.

## Mapping to a release train

For each element of the model: does prior art support it, what do the stores change, what is open.

1. changie fragments required per PR, changelog batch PR.
   - Prior art: no fragment tool anywhere. UBO and Dark Reader hand-edit `CHANGELOG.md` in the release commit; Refined GitHub relies on GitHub generated notes on a draft release; Bitwarden's changelog handling not read. The fragment model therefore has no support, but nothing contradicts it.
   - Stores: no store takes the changelog from the repo. AMO has a per-version release notes field settable through `--amo-metadata` (Refined GitHub passes just a link). The CWS API reference pages read show no release-notes field (unverified). The batched changelog therefore feeds the GitHub release body and AMO release notes only.
   - Open: whether AMO release notes carry the rendered batch or a link; whether the nightly (unlisted) release gets the same text.

2. Nightly calver train `YYYY.MM.DD` with `.NN` recuts, newest green commit on main.
   - Prior art: calver is used by Refined GitHub (daily-version-action) and Bitwarden (`YYYY.M.patch`); nightly-style prerelease builds on GitHub only is uBO's dev channel. No prior art picks "newest green commit" automatically; they tag on dispatch or by hand.
   - Stores: the manifest version must be unpadded (`2026.10.5`; `2026.10.05` is invalid), at most four segments (`.NN` must be one unpadded integer, with no channel segment), each integer at most 65535 for Chrome. Every upload must out-rank the previous one in the same listing and AMO burns each number permanently (even for unlisted). Nightly uploads to a store listing also trigger a review each time and CWS flags significant code changes. A nightly should therefore live on GitHub prereleases and an AMO unlisted/self-hosted channel (the uBO pattern) or a separate CWS listing (Bitwarden's `chrome-beta`), and stay off the public listing.
   - Open: tag spelling vs manifest spelling (uBO differs: `1.75.1b16` vs `1.75.1.16`); whether to use `version_name` for the human label; whether nightlies get their own add-on id/cws listing.

3. Release-bot GitHub app opens the changelog batch PR via merge queue and creates the tag; ruleset admits only that app.
   - Prior art: closest is Bitwarden's `repository-management.yml`, a dispatch that opens a "Bump client version(s)" PR but creates no tag. App-created tags plus a ruleset restricting tag creation are not seen in any project read.
   - Stores: no effect; the stores never see the tag. One consequence: because the version is stamped into the manifest at build time (Refined GitHub's `yq` step) the repo needs no version-bump commit, which suits a calver train; Dark Reader and uBO bump files by hand instead.
   - Open: stamp at build time (no bump commit) or keep a version file in the bump PR.

4. Tag-and-dispatch to a nightly deploy; prod only on manual dispatch of the same tag.
   - Prior art: Refined GitHub is the template (dispatch, then a draft release, then `Chrome` and `Firefox` jobs in GitHub environments). UBO and Dark Reader stop at a GitHub release (uBO hard-codes draft prerelease). Nobody read has two stages.
   - Stores: "same tag, same artifact" runs into two rules. (A) AMO version numbers are unique across channels; the exact nightly version cannot be submitted again to the listed channel after being signed unlisted (inferred from the unique-version rule; unverified for this exact case). UBO avoids it because dev builds and stable builds have different version numbers. (B) a prod build that must be reproducible from source for AMO should be built once and promoted instead of rebuilt. CWS offers a store-side second gate: `STAGED_PUBLISH` after approval (30 days to publish) and `deployInfos[].deployPercentage`, but partial rollout needs more than 10,000 weekly users, which likely rules it out for a small extension.
   - Open: promote the nightly artifact to prod (needs a separate AMO ID or a version scheme where the prod cut is a new recut, for example the next `.NN`) versus rebuilding the tag at prod time; whether prod waits for review (`--approval-timeout`) or just uploads.

5. Secrets and identity: PyPI trusted publishing for semver packages.
   - Prior art: every project that publishes uses long-lived secrets in GitHub environments (Refined GitHub: `EXTENSION_ID`, `CLIENT_ID`, `CLIENT_SECRET`, `REFRESH_TOKEN`, `WEB_EXT_API_KEY`, `WEB_EXT_API_SECRET`).
   - Stores: no OIDC or trusted publishing for CWS, AMO or Edge was found. CWS v2 offers a service account (impersonation avoids a downloaded key but needs a human-held identity to impersonate from; whether GitHub OIDC through workload identity federation works is untested), AMO uses a JWT key pair, Edge an API key that expires. Expect to rotate secrets.
   - Open: OAuth refresh token vs service account for CWS; one GitHub environment per store with required reviewers on the prod environment; rotation calendar for the Edge key.

6. Semver packages released separately.
   - Prior art: no extension project here separates its extension from a library release except Return YouTube Dislike, which versions extension and userscript independently (4.1.0 vs 3.2.1).
   - Stores: not applicable to extension packages; manifest versions are the extension's own.
   - Open: whether the userscript gets its own version line or shares the train version. Greasy Fork requires an incrementing `@version`; a calver `@version` (`2026.10.20`) is numeric and dot-joined, which Violentmonkey accepts; sharing the train version is possible.

7. Userscript hosting on GitHub release assets and Greasy Fork.
   - Prior art: RYD points `@updateURL`/`@downloadURL` at a committed file on `main` and CI-checks that it equals the build; uBO uses release assets with an update JSON; no project found uses `releases/latest/download/x.user.js` explicitly (the form is documented by GitHub).
   - Stores: `releases/latest/download/` skips prereleases and drafts, which maps well: nightlies are prereleases and never move the pointer, and promoting a release to non-prerelease makes the userscript update. The asset name must stay fixed. Greasy Fork strips/rewrites update URLs, forbids minified or obfuscated code (the userscript bundle must be built unminified) and warns on non-incrementing `@version`; its webhook sync fires on GitHub push or release events.
   - Open: sync from a release asset URL or from a file on a branch (RYD style); nightly userscript channel (separate asset name or separate release); whether Greasy Fork accepts a redirecting `releases/latest/download` URL (unverified).

8. AMO source submission and `corepack enable` instruction.
   - Prior art: Bitwarden builds a reviewer source zip in CI; Dark Reader stores AMO signatures to reproduce store archives; uBO ships plain source; Refined GitHub's step name mentions source but the command does not upload it.
   - Stores: AMO needs a no-difference rebuild, a readme with environment and commands, a lockfile, 200MB max; default reviewer environment is node 24.14.0 and npm 11.9.0 on Ubuntu 24.04.4, where corepack exists; node 25 removed it. `web-ext sign` has `--upload-source-code`; the API takes a multipart `source` field.
   - Open: have the release job upload the source zip with the listed submission (flag or v5 API) or keep it manual; pin `packageManager` with a hash; add the `npm install -g corepack` fallback line.
