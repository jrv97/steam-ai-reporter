# RQ1: Per-tab toolbar action state (setIcon, enable, disable) in Chrome and Firefox MV3

Research date 2026-11-13. Question: can the toolbar icon look dimmed on tabs that are not `https://store.steampowered.com/*` and normal on store tabs, using `action.setIcon`, `action.enable` and `action.disable`, with no `host_permissions`? Tags: `unverified` means not confirmed by a primary source in this run; `inference` means a deduction from cited facts. Chromium files were read at main or HEAD on 2026-11-13 unless a revision is named. Some pages were read through a summarizing fetch tool, so code is paraphrased; where two reads agree the text says so.

## Answer in short

- No permission is needed in either browser to call `action.setIcon`, `action.enable` or `action.disable`. Chrome's `action.json` schema lists no permissions for the namespace or these three functions; MDN lists none. Only the `action` manifest key is required (the project manifest already has it). Content scripts cannot call `chrome.action`, so a background context must do the call; a content-script message gives it the `tabId` without a `tabs` permission.
- Tab-scoped values (call with `tabId`) are wiped on every committed top-level cross-document navigation in both browsers and kept across same-document navigations (pushState, hash). Tab close drops them too. Chrome wipes in `ExtensionActionRunner::DidFinishNavigation`; Firefox wipes in `PanelActionBase.handleLocationChange` when `fromBrowse` is true. bfcache restore and prerender activation (Chrome) are `inference`: both are committed primary-main-frame navigations, so they should wipe too.
- A disabled action renders differently in each browser. Chrome grays the icon only when the action is disabled AND the extension has no site access on that tab (site interaction `kNone`); where it has access, `disable()` does not gray it. Firefox dims the button with opacity through the `disabled` attribute. A disabled action does not open its popup in either browser (Chrome shows the context menu on click instead). Since this project's popup is the settings page, `disable()` would lock it on off-store tabs; swapping icons with `setIcon` avoids that. Chrome can start disabled through `action.default_state: "disabled"`; Firefox has no such key (not in browser-compat-data).
- Global values (no `tabId`) are in-memory. Firefox: `this.globals` is a plain object; only the manifest icon is cached at startup. Chrome: no documented persistence for MV3 `action`; an old Chromium storage manager persisted only default `browser_action` values (MV2 era, current MV3 behavior `unverified`); a W3C issue says both browsers forget `action.*` changes on restart. Only the manifest (`default_icon`, `default_state`) is a reliable baseline across restarts.
- Firefox for Android 142 and later: `action`, `setIcon`, `enable`, `disable` and `default_icon` are supported (browser-compat-data mirrors desktop 109). The action shows as an item in the Add-ons/Extensions menu, not on a toolbar. In a Chrome MV3 service worker, `path` works for `setIcon`: the renderer binding fetches the file and draws it on an `OffscreenCanvas`. PNG only; a relative path goes to `fetch` unchanged.

## Findings

### 1. Permissions for setIcon, enable, disable

Chrome: the `action` namespace in Chromium's API schema has no `permissions` field, and `setIcon`, `enable`, `disable` carry none. (source: https://raw.githubusercontent.com/chromium/chromium/main/chrome/common/extensions/api/action.json) The reference page lists no permission for the API, and says `"manifest_version": 3` plus an `"action"` key are needed to use `chrome.action`; without `"action"` the extension still shows in the toolbar menu only. (source: https://developer.chrome.com/docs/extensions/reference/api/action)

Firefox: the MDN page for `action.setIcon` lists no permission and says the API is available in MV3. (source: https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/api/action/seticon/index.md) The Firefox schema file was not readable in this run (the paths tried returned 404), so the schema-level check is `unverified` for Firefox. The implementation file shows no permission check around these calls, only `menus` or `contextMenus` for the context menu. (source: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/browser/components/extensions/parent/ext-browserAction.js)

Who can call: Chrome lists only `dom`, `i18n`, `storage` and a few `runtime` members as directly available to content scripts, so `chrome.action` is not among them. (source: https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts) The call must come from a service worker (Chrome), an event page (Firefox) or an extension page such as the popup. A content script can send a message; `runtime.MessageSender.tab` is present when the connection was opened from a tab, including a content script, so the background learns the `tabId` without a `tabs` permission. (source: https://developer.chrome.com/docs/extensions/reference/api/runtime) Whether `sender.tab.url` is filled without the `tabs` permission was not stated on that page; the design below does not need it.

### 2. When tab-scoped state is cleared

Both browsers keep two layers: a global value and per-tab overrides. A per-tab value wins; without one the global value shows. Chrome: a code comment says instances can have both global and per-tab state, global state is stored under `kDefaultTabId`, and lookups fall back to the global value. (source: https://chromium.googlesource.com/chromium/src/+/HEAD/extensions/browser/extension_action.h) Chrome docs: tab-specific values take priority over global ones, and tab-specific state is automatically reset when the tab is closed. (source: https://developer.chrome.com/docs/extensions/reference/api/action) Firefox: `setProperty(target, prop, value)` writes into `getContextData(target)`; that returns `tabContext.get(target)` for a tab or `this.globals` otherwise; `globals` is `Object.create(this.defaults)`, so tab and window values fall back to defaults through the prototype chain. (source: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/toolkit/components/extensions/ExtensionActions.sys.mjs)

#### Chrome

The clearing call is `ExtensionActionDispatcher::ClearAllValuesForTab(web_contents, web_contents_being_destroyed)`. It loops over enabled extensions, calls `ExtensionAction::ClearAllValuesForTab(tab_id)` on each, then notifies observers. (sources: https://chromium.googlesource.com/chromium/src/+/HEAD/chrome/browser/extensions/extension_action_dispatcher.cc, https://chromium.googlesource.com/chromium/src/+/HEAD/chrome/browser/extensions/extension_action_dispatcher.h) `ExtensionAction::ClearAllValuesForTab(TabID)` erases the per-tab `icon_` and `is_visible_` entries (among others); the header says it removes all tab-specific state except declarative state. (sources: https://chromium.googlesource.com/chromium/src/+/HEAD/extensions/browser/extension_action.cc, https://chromium.googlesource.com/chromium/src/+/HEAD/extensions/browser/extension_action.h)

The two callers are in `ExtensionActionRunner`, a `content::WebContentsObserver` (read twice, googlesource HEAD and the raw GitHub mirror, same code):

- `DidFinishNavigation` returns early when `!navigation_handle->IsInPrimaryMainFrame() || !navigation_handle->HasCommitted() || navigation_handle->IsSameDocument()`. Otherwise it resets page-request state and calls `ExtensionActionDispatcher::Get(browser_context_)->ClearAllValuesForTab(web_contents())`. (sources: https://chromium.googlesource.com/chromium/src/+/HEAD/chrome/browser/extensions/extension_action_runner.cc, https://raw.githubusercontent.com/chromium/chromium/main/chrome/browser/extensions/extension_action_runner.cc)
- `WebContentsDestroyed` always calls `ClearAllValuesForTab(web_contents(), /*web_contents_being_destroyed=*/true)`. (same sources)

Result by case:

- Cross-document top-level navigation, committed: cleared. Navigations that become downloads or return 204/205 do not commit, so they do not clear. (sources: ExtensionActionRunner above; `HasCommitted` comment in https://raw.githubusercontent.com/chromium/chromium/main/content/public/browser/navigation_handle.h)
- Subframe navigation: not cleared (`IsInPrimaryMainFrame()` is false).
- Same-document navigation (fragment, pushState, replaceState, same-page history navigation): not cleared. `NavigationHandle::IsSameDocument` documents these examples, and `WebContentsObserver::DidFinishNavigation` is documented as firing for them, which is why the guard exists. (sources: navigation_handle.h above, https://raw.githubusercontent.com/chromium/chromium/main/content/public/browser/web_contents_observer.h)
- Tab close: cleared by `WebContentsDestroyed`; Chrome docs say the same. (sources: ExtensionActionRunner above, action docs above)
- Back/forward cache restore: `inference`, wiped. `NavigationHandle::IsServedFromBackForwardCache` exists because observers get navigation handles for restores, and a restore is a committed cross-document navigation in the primary main frame, so the guard passes. No Chromium text read says this about extension actions. (sources: navigation_handle.h and web_contents_observer.h above)
- Prerender activation: `inference`, wiped at activation. `IsPrerenderedPageActivation` exists on `NavigationHandle`, and the activation commits in the primary main frame. The prerender itself lives in an additional frame tree where `IsInPrimaryMainFrame()` is false (the header says a WebContents may have additional frame trees for prerendering pages), so pre-rendering does not wipe the visible tab's state. (source: navigation_handle.h above)

#### Firefox

`TabContext` lives in `ext-browser.js`. Its `onLocationChange(browser, webProgress, request, locationURI, flags)` ignores non-top-level changes, then computes `fromBrowse = !(flags & Ci.nsIWebProgressListener.LOCATION_CHANGE_SAME_DOCUMENT)` (the code comment says it is false for hash changes and `history.pushState`) and emits `location-change` with that flag. `TabContext.clear(tab)` deletes the tab entry. (source: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/browser/components/extensions/parent/ext-browser.js)

`PanelActionBase`, the base of `BrowserActionBase`, subscribes with `this.tabContext.on("location-change", this.handleLocationChange.bind(this))`. `handleLocationChange(eventType, tab, fromBrowse)` calls `this.tabContext.clear(tab)` only `if (fromBrowse)`. `BrowserActionBase.handleLocationChange` then calls `updateOnChange(tab)` when `fromBrowse`. (source: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/toolkit/components/extensions/ExtensionActions.sys.mjs)

Result by case:

- Cross-document top-level navigation: cleared.
- Same-document navigation (hash, pushState): not cleared.
- Tab close: `TabContext.tabData` is a `WeakMap` keyed by the tab, and `TabContext` listens to no `TabClose`; the entry goes when the tab object is collected. For the extension the effect is the same. (source: ext-browser.js above)
- Back/forward cache restore: `inference`, wiped. A session-history navigation to another document is a top-level location change without the same-document flag, so `fromBrowse` is true. The files read do not mention bfcache or `pageshow`.
- Prerender: the files read have no prerender activation path; not applicable (`unverified` beyond that).
- MDN and BCD: the `action.setIcon` page says the tab-specific icon resets when the user navigates the tab to a new page. (source: https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/api/action/seticon/index.md) For `browserAction.setIcon`, Firefox before 58 did not clear tab-specific icons on page load. (source: https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/api/browserAction.json)

#### Consequence for a "dim off-store" scheme (inference)

- A per-tab override is lost on each cross-document load, so a per-tab "normal icon" must be re-applied after every store page load and after every bfcache restore. A store content script runs once per document load and can message the background; a bfcache restore does not re-run it, so a `pageshow` handler with `event.persisted` would be needed (`pageshow.persisted` semantics were not researched here).
- The baseline on off-store tabs is the global value. The safest baseline is the manifest: a dimmed `default_icon` there, and a per-tab `setIcon({tabId})` with the normal icon on store tabs. When a store tab navigates away, the wipe rules above return it to the dim baseline with no extra code.
- A runtime-set global icon would not survive a restart (see 4), another reason to keep the baseline in the manifest.
- This design needs a background context, which project rule 3 in AGENTS.md allows only with an ADR (a project rule, not a platform fact). It needs neither `tabs` nor `host_permissions` (see 1).

### 3. How a disabled action renders and behaves

#### Chrome

Behavior: per the docs, `enable()` and `disable()` only control whether the popup or `action.onClicked` fires; the icon stays in the toolbar. Actions are enabled by default. (source: https://developer.chrome.com/docs/extensions/reference/api/action)

Rendering: `ExtensionActionViewModel::GetIconImageSource` sets grayscale with a code comment that the icon is grayscaled only if it cannot interact with the page and the icon is disabled. The flag is `!action_is_visible && !has_side_panel_action && site interaction == kNone`. `action_is_visible` is the per-tab visibility that `enable` and `disable` set (`ExtensionAction::SetIsVisible`). (sources: https://chromium.googlesource.com/chromium/src/+/HEAD/chrome/browser/ui/extensions/extension_action_view_model.cc; the older revision https://chromium.googlesource.com/chromium/src/+/9e001703a2/chrome/browser/ui/extensions/extension_action_view_controller.cc has the same two conditions; `SetIsVisible`: https://chromium.googlesource.com/chromium/src/+/HEAD/extensions/browser/extension_action.cc) `set_grayscale` is applied before the `kExtensionsMenuAccessControl` early return, so that feature flag does not skip it. (source: extension_action_view_model.cc above)

The gray is `gfx::ImageSkiaOperations::CreateHSLShiftedImage(skia, {-1, 0, 0.6})` in `IconWithBadgeImageSource::Draw`, with no alpha change; the badge is not grayed. (sources: https://raw.githubusercontent.com/chromium/chromium/main/chrome/browser/ui/extensions/icon_with_badge_image_source.cc; header comment "Whether or not the icon should be grayscaled (e.g., to show it is disabled)": https://chromium.googlesource.com/chromium/src/+/HEAD/chrome/browser/ui/extensions/icon_with_badge_image_source.h) How strong the shift looks on this project's icon was not tested: `inference`, check on a sample.

Site-access nuance: with site interaction other than `kNone` (granted, withheld or activeTab), the icon is not grayed even when disabled, and `IsEnabled()` returns true for `kWithheld` and `kActiveTab`. (source: extension_action_view_model.cc above) For this project (content script match on the store only, no `host_permissions`, no `activeTab`), off-store tabs should be `kNone` and gray; a disabled store tab would not gray. `inference`: the mapping from manifest content-script matches to `SiteInteraction` values was not read; test on a real build.

Click: `ExecuteUserAction` calls `IsEnabled(web_contents)`; when false it closes the extensions menu, calls `delegate_->ShowContextMenuAsFallback()` and returns, so the popup does not open and the context menu shows instead. `GetContextMenu()` and `GetTooltip()` have no `IsEnabled` check, so right-click and the tooltip still work. (source: extension_action_view_model.cc above; the older revision above agrees on the `ShowContextMenuAsFallback` branch)

Start disabled: yes. The manifest `action.default_state` accepts `"enabled"` (default) or `"disabled"`; with `"disabled"` the action is disabled by default and must be enabled programmatically. (source: https://developer.chrome.com/docs/extensions/reference/api/action) The parser accepts only those two strings and allows the key only for the `action` type (`ActionInfo::Type::kAction`); other types get an error. (source: https://chromium.googlesource.com/chromium/src/+/ad276a611599253ccb901b2957224efcbfc01cbc/extensions/common/api/extension_action/action_info.cc, revision `ad276a6`; the current file path 404ed, so the current parser is `unverified`, but the public docs agree) The `declarativeContent` example in the docs disables the action in `runtime.onInstalled` and enables it per site. (source: action docs above) The manifest value is the global default (`kDefaultTabId`); a per-tab `enable(tabId)` overrides it and is wiped on navigation (see 2). (source: the `ExtensionAction` constructor reads `default_state_ == ActionInfo::DefaultState::kEnabled` for the default tab, https://chromium.googlesource.com/chromium/src/+/HEAD/extensions/browser/extension_action.cc)

Firefox has no such key: browser-compat-data for manifest `action` lists `default_icon`, `default_popup`, `default_title`, `default_area`, `theme_icons` and `browser_style`, and no `default_state`. (source: https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/manifest/action.json) Whether Firefox warns on this Chrome-only key in a shared manifest was not checked: `unverified`.

#### Firefox

Behavior: `updateButton` sets `button.setAttribute("disabled", "true")` when `tabData.enabled` is false and removes it when true. `BrowserActionBase.isShownForTab(tab)` returns `getProperty(tab, "enabled")`, and `triggerClickOrPopup` returns early when `!isShownForTab(tab)`, so no click event and no popup. Middle-click (`auxclick`) also checks `enabled`. (sources: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/browser/components/extensions/parent/ext-browserAction.js, https://raw.githubusercontent.com/mozilla-firefox/firefox/main/toolkit/components/extensions/ExtensionActions.sys.mjs) Bug 1307551 stopped pre-loading the popup of a disabled browserAction (Firefox 52, VERIFIED FIXED). (source: https://bugzilla.mozilla.org/show_bug.cgi?id=1307551) The MDN `disable` page says only that the action cannot be clicked while the tab is active and says nothing about appearance. (source: https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/api/action/disable/index.md)

Rendering: an opacity dim, not grayscale. In `toolbarbuttons.css`, a disabled `.toolbarbutton-1` gets `opacity` from the `toolbarbutton-opacity-disabled` design token (a CSS custom property, restored to 1 in customize mode). The token is defined elsewhere and its value was not read; the older rule was `opacity: .4`, quoted in Bug 1204609. (sources: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/browser/themes/shared/toolbarbuttons.css, https://bugzilla.mozilla.org/show_bug.cgi?id=1204609) Bug 1204609 (fixed for Firefox 55, rev 58119f6aff8f) made disabled badged extension buttons dim too, because the old rule targeted only `.toolbarbutton-icon` directly under the button. (source: https://bugzilla.mozilla.org/show_bug.cgi?id=1204609) In the Unified Extensions panel `ext-browserAction.js` has no separate disabled branch; the look comes from the `disabled` attribute. The only `[disabled]` rules in `unified-extensions.css` sit in a `prefers-contrast` block (`color: GrayText`, `opacity: 1 !important`), so the panel dim in a normal theme is `unverified` (it may come from `panelUI-shared.css`, not read). (sources: ext-browserAction.js above, https://raw.githubusercontent.com/mozilla-firefox/firefox/main/browser/themes/shared/addons/unified-extensions.css)

Context menu: `ext-browserAction.js` has no disabled branch for the context menu (it is built on `popupshowing` in `updateContextMenu`), but whether the XUL button still delivers `contextmenu` while `disabled="true"` was not confirmed: `unverified`. (source: ext-browserAction.js above)

### 4. Persistence of global values across browser restart

Firefox: global values live in `this.globals` (`Object.create(this.defaults)`), an in-memory object. Defaults come from the manifest through `loadIconData()`, which reads `StartupCache` with the key `["browserAction", "default_icon_data"]`; that caches the manifest icon only. The files read have no write of API-set values to disk. (sources: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/toolkit/components/extensions/ExtensionActions.sys.mjs, https://raw.githubusercontent.com/mozilla-firefox/firefox/main/browser/components/extensions/parent/ext-browserAction.js) Conclusion `inference` from that absence: a global `setIcon` or `disable()` does not survive a restart and the manifest state returns. A Mozilla Discourse thread on MV3 action icons suggests re-applying in both `runtime.onInstalled` and `runtime.onStartup` (forum, found by search, not fetched). (source: https://discourse.mozilla.org/t/mv3-and-customizable-action-icon-and-title/111716)

Chrome: the in-memory `ExtensionAction` is created lazily from the manifest `ActionInfo` by `ExtensionActionManager::GetExtensionAction`, kept in an `actions_` map and destroyed on unload; that file has no prefs code. (source: https://raw.githubusercontent.com/chromium/chromium/main/extensions/browser/extension_action_manager.cc) A separate `ExtensionActionStorageManager` persists default-tab values (popup URL, title, badge text and colors, `appearance`, icon) of `TYPE_BROWSER` actions into the extension state store. It writes only when `web_contents` is null, with the comment that only default settings are persisted because per-tab settings cannot be persisted across browser sessions. (source: revision `486e9d5`, 2019, MV2 era: https://chromium.googlesource.com/chromium/src/+/486e9d5/chrome/browser/extensions/extension_action_storage_manager.cc) A search-engine snippet of the current file says the load path returns early unless the type is `kBrowser`, which would exclude MV3 `kAction` extensions; the current file could not be fetched (HEAD, main and lkgr paths all 404), so this is `unverified`. The Chrome reference page says nothing about restart persistence for action state. (source: https://developer.chrome.com/docs/extensions/reference/api/action)

W3C WebExtensions Community Group issue 249 (opened 2022-07-25, label "proposal", shelved 2022-09-01, still open) states that browsers forget `action.*` customizations on browser restart and that extensions re-apply them in `runtime.onStartup`, which is slow and flickers. This is the proposer's claim, not a maintainer finding. (source: https://github.com/w3c/webextensions/issues/249) BCD notes for legacy Edge `setIcon`: "This call is not persisted." (source: https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/api/browserAction.json)

Practical reading: do not rely on a runtime-set global value in either browser; keep the baseline in the manifest (`default_icon`, and in Chrome `default_state`). Within one browser session a Chrome global value does outlive service-worker restarts, because the `ExtensionAction` lives in the browser process; the docs example that calls `disable()` in `onInstalled` relies on this without stating it. (source: action docs above; the reliance is `inference`)

### 5. Firefox for Android 142 and later

Support from browser-compat-data: `webextensions.api.action` is Firefox 109 with Firefox Android "mirror" (same, 109). `action.setIcon`, `action.disable` and `action.enable` are the same (109, mirror). Sub-features: `imageData` Firefox 109, `windowId` Firefox 109, `null` reset Firefox 109, `details_variants_parameter` not supported in Chrome or Firefox. (source: https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/api/action.json; read through a summarizing fetch, so the Android `mirror` entries are taken as stated there) For the MV2 `browserAction`, Android `setIcon`, `enable` and `disable` are 79, and the top-level entry is 55 with the note "Available for use in Manifest V2 only." (source: https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/api/browserAction.json) Manifest `action` keys: `default_icon` 109 (Android mirror), `default_popup` 109 (mirror), `default_title` 109 with the Android note "Browser actions are presented as menu items, and the title is the menu item's label", `default_area` and `theme_icons` unsupported on Android. (source: https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/manifest/action.json) The project's `gecko_android.strict_min_version` is 142.0, above all of these. (source: repo file src/platform/extension/manifest.gecko.json)

Where the action shows: Extension Workshop says `browserAction`, `action` and `pageAction` buttons appear under the Add-ons item in the browser menu, not in the toolbar, and popups open as an overlay covering the browser window. (source: https://extensionworkshop.com/documentation/develop/differences-between-desktop-and-android-extensions/)

How the row renders: android-components `WebExtensionBrowserMenuItem` calls `loadIcon` with the view height and sets the drawable. It falls back to the generic extension icon (`mozac_ic_extension_fill_24`) only when loading throws. The row's enabled flag is `action.enabled ?: true`, and the file applies no alpha change, so a disabled row's look comes from the layout or menu theme. (source: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/mobile/android/android-components/components/browser/menu/src/main/java/mozilla/components/browser/menu/item/WebExtensionBrowserMenuItem.kt, one summarizing read) So on Android the icon appears inside the menu row next to the title, and per-tab `setIcon`, `enable` and `disable` reach the row through the same `Action` fields (`enabled`, `loadIcon`, `title`).

Not verified: the Fenix menu-redesign file that draws the extension rows in the current menu (a Discourse report on pageAction breaking on Firefox 142 traces it to Bug 1910814) was not found at the paths tried (404). Whether a disabled row looks dim in the redesigned menu, and whether the per-tab state refreshes when the menu reopens, are `unverified`. (source for the 142 report, not fetched: https://discourse.mozilla.org/t/page-action-pageaction-is-broken-on-firefox-142-for-android/145845)

Consequence (inference): on Android there is no toolbar icon to dim; the dim or normal icon shows in the menu row only, so the behavior differs from desktop and needs a device test on Firefox 142 or later.

### 6. `path` versus `imageData` for setIcon in a Chrome MV3 service worker

`path` works in a service worker. Chromium's renderer-side binding `set_icon.js` picks a loader with `requireNative('utils').isInServiceWorker()`. In a service worker, `loadImagePathForServiceWorker` runs `fetch(path)`, rejects a non-OK response ("Response from fetching icon not ok."), reads a blob, calls `createImageBitmap(blob)`, draws it on an `OffscreenCanvas` and hands the `ImageData` on; elsewhere it uses `new Image()` and a `<canvas>`. A `{size: path}` map loads each entry and calls `SetIconCommon` once all finish; an empty map throws "The path property must not be empty."; only the first failure is reported, as "Failed to set icon '<path>': ...". (sources: https://raw.githubusercontent.com/chromium/chromium/main/extensions/renderer/resources/set_icon.js, https://chromium.googlesource.com/chromium/src/+/main/extensions/renderer/resources/set_icon.js; two separate reads agree) The Chrome docs describe both `path` and `imageData` as valid and show `imageData` from an `OffscreenCanvas` as the service-worker example; they do not say how a relative `path` resolves from a service worker. (source: https://developer.chrome.com/docs/extensions/reference/api/action)

Caveats:

- Relative path base: the binding passes `path` unchanged to `fetch`, so it resolves by `fetch` rules against the service worker's script URL (`inference`). A worker at `dist/background.js` resolving `icons/dim-16.png` would request `dist/icons/dim-16.png`. A leading-slash path (extension root) or `chrome.runtime.getURL("icons/dim-16.png")` avoids the ambiguity (`inference`; `getURL` is on the content-script API list and is a `runtime` method). The binding file has no `getURL` call. (source: set_icon.js above)
- Format: the worker decodes the blob with `createImageBitmap`. The Chrome docs say SVG is not supported and unpacked extensions must use PNG. (source: https://developer.chrome.com/docs/extensions/reference/api/action) A Stack Overflow report that SVG fails to decode in a service worker (found by search, not fetched) agrees; it is not a primary source.
- Cost: each `path` call fetches and decodes the files again. In a store-load flow the worker wakes on the content-script message, then fetches and decodes per page load. No timing was measured; `imageData` built per wake costs a similar decode (`inference`).
- Size keys: a single `ImageData` is keyed by its width; a size-keyed object has each entry verified. (source: set_icon.js above)
- Firefox: both `path` and `imageData` are accepted. `normalizeIcon` delegates to `IconDetails.normalize`, which was not read, so how a relative `path` resolves in the background page is `unverified`. (source: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/toolkit/components/extensions/ExtensionActions.sys.mjs)

## Caveats and version notes

- Several Chromium files moved or returned 404 (`extension_action_storage_manager.cc`, `extension_action_view_controller.cc` now `extension_action_view_model.cc`, `extensions/common/api/extension_action/action_info.cc`). Where an old revision is cited, it is named.
- The Chromium notes in 2 on bfcache and prerender are deductions from `NavigationHandle` and `WebContentsObserver` API comments, not from a statement about extension actions.
- Firefox source was read from `raw.githubusercontent.com/mozilla-firefox/firefox/main` (the GitHub mirror of mozilla-central). searchfox.org pages returned only revision lists through the fetch tool, so searchfox was not used for code.
- Dimming differs by browser (Chrome: HSL grayscale only without site access; Firefox: opacity token). Swapping between a normal and a pre-dimmed PNG pair with `setIcon` (and a dim `default_icon` as the baseline) gives the same look in both and keeps the popup usable. `disable()` is only needed if clicks must be blocked. `inference`.
- `action.default_state` is a Chrome-only manifest key (no BCD key for Firefox); shipping it in a manifest shared with Firefox needs a Firefox load test for warnings. `unverified`.
- Firefox Android: the Fenix menu redesign shipped within the 133 to 142 range (Bugs 1921530 and 1910814 appear in search results); `action` rendering in the redesigned menu on 142 was not verified on a device.
- Not covered: `declarativeContent.SetIcon` (Chrome only, needs the `declarativeContent` permission) and Firefox `pageAction` `show_matches`; both add a permission or a second API.
