# RQ2: Background context and alternatives for a store-only toolbar icon

Research date 2026-11-13. Question: the toolbar icon should read dimmed on tabs that are not `https://store.steampowered.com/*` and normal on store tabs. Today the extension has `storage`, one store content script, no `host_permissions` and no background. Content scripts cannot call the `action` API. This note covers what a background context costs, what works without one, and how uBlock Origin does it. Tags: `unverified` means not confirmed by a primary source in this run; `inference` means a deduction from cited facts.

## Answer in short

- A background context is free at install: neither a `background` manifest key nor `storage` carries a permission warning in Chrome, CWS review docs do not name background code as a trigger, and AMO policy text names none. One manifest may carry `background.service_worker` and `background.scripts`; Chrome 121 and later ignores `scripts`, Firefox ignores `service_worker` (it does not support it, bug 1573659 still open). AMO's linter warns (`BACKGROUND_SERVICE_WORKER_IGNORED`) and errors only if `service_worker` appears without `scripts`.
- `sender.tab.id` reaches the background with no `tabs` permission in both browsers; only `url`, `pendingUrl` (Chrome), `title` and `favIconUrl` are gated. `sender.url`, `sender.origin` and `sender.frameId` need no permission, so the background can check origin and top frame itself.
- Warning-free cross-browser pattern (inference): manifest `default_icon` is the dimmed set; the store content script sends one message per page load; the background calls `action.setIcon({ tabId, ... })` with the normal set. Tab-scoped icon values reset on navigation (documented for Firefox; Chrome only by a 2010 maintainer statement and a 2014 review, `unverified` on current source), so non-store tabs fall back to the dim default. Do not use `webNavigation` (warns "Read your browsing history.") or `tabs` (same warning).
- Chrome-only options with no runtime JS: `declarativeContent` has no warning, supports `ShowAction` and `SetIcon` (imageData only in practice; `path` is commented out in the source), rules persist. `ShowAction` needs `action.default_state: "disabled"`, which also stops the popup opening on other tabs (click opens the context menu). Firefox has no `declarativeContent`; `page_action` `show_matches` still exists in MV3 but draws in the address bar, not the toolbar.
- No viable background-free route exists on Firefox: an extension iframe made by a content script has no `tabs` or `windows` API there (Mozilla test), so it cannot learn its tab id. Chrome probably allows it, at the cost of a web-accessible resource.

## Findings

### 1. Background context: install warnings, store review, manifest keys

Chrome permission warnings. The permissions list has no warning for `storage`, `declarativeContent`, `scripting`, `activeTab` and the `background` permission; warnings exist for `tabs` ("Read your browsing history.") and `webNavigation` (same text). (Source: https://developer.chrome.com/docs/extensions/reference/permissions-list, read twice with different prompts) The `background` manifest key is not a permission, so declaring a service worker adds nothing to the list. The `background` permission (start Chrome early, shut down late) is a different thing and also has no warning. (Source: https://developer.chrome.com/docs/extensions/reference/permissions-list)

Chrome upgrade prompts. The permission-warnings page says changes to `permissions`, `content_scripts.matches` and `host_permissions` may trigger warnings; a background key is not on that list. (Source: https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)

Chrome Web Store review. The review-process page lists these as signals for closer review: new developers, new extensions, "dangerous permission requests", "significant code changes"; broad host permissions such as `<all_urls>` lengthen review; obfuscation is disallowed. Background scripts and service workers are not mentioned. (Source: https://developer.chrome.com/docs/webstore/review-process) So adding a service worker does not trigger documented extra review; `inference`: a new `background` key counts as a code change like any other.

AMO. The add-on policies page says add-ons request only the permissions they need; the first 100000 characters read do not mention background scripts or pages (final ~6600 characters unread). (Source: https://extensionworkshop.com/documentation/publish/add-on-policies/) Firefox install prompts come from permissions, and MDN's `permissions` page says only that a browser "may inform the user at install time"; it gives no table, so the exact Firefox prompt text for `storage` is `unverified` here. (Source: https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/manifest.json/permissions/index.md) The support.mozilla.org permission-message page failed to load in this run.

Firefox MV3 background support. `background.service_worker` is not supported (Firefox bug 1573659); Firefox runs `scripts` (or `page`) when `service_worker` is absent or ignored. BCD records `service_worker` for Firefox as `false` and `scripts` since Firefox 48. (Sources: https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/manifest.json/background/index.md, https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/manifest/background.json) Bug 1573659 is the open meta bug "Background Service Worker for Manifest v3": status NEW, no target milestone, 17 open dependencies, last touched about 9 days before this run. (Source: https://bugzilla.mozilla.org/show_bug.cgi?id=1573659, one fetch) Conclusion for late 2026: Firefox has no service worker background and shows no committed plan; keep `scripts`.

Both keys in one manifest. MDN says specifying both supports cross-browser MV3: Chrome uses `service_worker`, Firefox uses `scripts`; `preferred_environment` is not required. Before Chrome 121 Chrome refuses an MV3 manifest with `background.scripts` or `background.page`; from 121 it ignores them. Before Firefox 120 a present `service_worker` kept the page from starting; from 121 it starts as expected. (Source: https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/manifest.json/background/index.md) SteamDB ships exactly this: `scripts: ["scripts/background.js"]` and `service_worker: "scripts/background.js"`, MV3, `strict_min_version` 128.0. (Source: https://raw.githubusercontent.com/SteamDatabase/BrowserExtension/master/manifest.json) The project's Gecko floor is 140, above both Firefox thresholds.

AMO linter. Rule `BACKGROUND_SERVICE_WORKER_IGNORED` is a warning ("unsupported and ignored on Firefox"); `BACKGROUND_SERVICE_WORKER_NOFALLBACK` is an error when `service_worker` is not paired with `scripts`. (Source: https://mozilla.github.io/addons-linter/) Expect one linter warning for a shared manifest; a per-browser manifest (service_worker for Chrome, scripts for Firefox) avoids it. `unverified`: whether the linter still emits the warning when both keys are present, since the rule text only names the ignored property.

Project rule. AGENTS.md rule 3 says no background script unless an ADR says otherwise, so this choice needs an ADR. (Source: local file AGENTS.md)

### 2. Content script runtime.sendMessage and sender.tab.id without `tabs`

Content scripts can call `runtime.sendMessage` directly (Chrome lists `runtime.sendMessage()`, `runtime.connect()`, `runtime.onMessage`, `storage`, `i18n` as the direct APIs; MDN lists `runtime`, `extension`, `i18n`, `menus.getTargetElement` and `storage`). No `action`, `browserAction` or `tabs` namespace is available to them. (Sources: https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts, https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/content_scripts/index.md)

`MessageSender.tab` is present when the sender is a tab, including content scripts, and `frameId` is 0 for the top frame and set only when `tab` is set; `url` is the sending frame's own URL and `origin` is its origin. MDN lists no permission condition for these properties. (Sources: https://developer.chrome.com/docs/extensions/reference/api/runtime, https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/api/runtime/messagesender/index.md)

Which Tab fields are hidden. Chrome gates `url`, `pendingUrl`, `title` and `favIconUrl` on the `tabs` permission or a host permission for the page; `Tab.id` carries no condition. `tabs.query` filters on `url` and `title` are ignored without access. (Source: https://developer.chrome.com/docs/extensions/reference/api/tabs) Firefox gates `url`, `title` and `favIconUrl` the same way; host-permission access works in Firefox 86 and later and Chrome 50 and later; MDN says "You can use most of this API without any special permission". `Tab.id` has no listed condition and is unique within a browser session. (Sources: https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/api/tabs/index.md, https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/api/tabs/tab/index.md)

Consequence (inference): `sender.tab.id` suffices for `action.setIcon({ tabId })` in both browsers with permissions `["storage"]` only. The background should still verify `sender.origin` equals the store origin and `sender.frameId` is 0 instead of trusting the payload; the Chromium security note on content-script fetches makes the same point about not trusting content-script input. (Source: https://www.chromium.org/Home/chromium-security/extension-content-script-fetches/, cited in the sibling note rq5)

The `action` API needs no manifest permission; it needs the `action` manifest key. The permissions list has no `action` entry. (Source: https://developer.chrome.com/docs/extensions/reference/permissions-list; Chromium feature file gives `action` dependency `manifest:action`, https://raw.githubusercontent.com/chromium/chromium/main/chrome/common/extensions/api/_api_features.json)

`action.setIcon` details. Both `path` and `imageData` take a single value or a size-keyed dictionary. `tabId` limits the change to that tab; omitting it sets the global value; tab-specific values take priority. Chrome docs: icons are 16 DIP and multiple sizes are recommended; "SVG isn't supported" (use PNG or imageData); tab-scoped values "automatically reset when the tab is closed". (Source: https://developer.chrome.com/docs/extensions/reference/api/action) MDN for Firefox: `tabId` "sets the icon only for the given tab" and the icon "is reset when the user navigates this tab to a new page"; tabs without their own icon inherit the global icon, which defaults to the manifest `default_icon`; passing both `tabId` and `windowId` fails; Firefox `action` is available from 109. (Sources: https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/api/action/seticon/index.md, https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/api/action.json)

Navigation reset in Chrome. The current Chrome docs do not state it. A Chromium maintainer wrote in 2010 that the badge `tabId` "is really the tabId, but only until a navigation occurs". (Source: https://groups.google.com/a/chromium.org/g/chromium-extensions/c/4chFiL0Bj9g/m/mqjzkinWTZAJ) A 2014 Chromium review added `ExtensionActionAPI::ClearAllValuesForTab` to clear all action values for a tab's WebContents; a search summary of the patch reports the caller used a `!is_in_page` condition, but the tab_helper diff was not readable. (Source: https://codereview.chromium.org/482993003/patch/80001/90002) Current `ExtensionAction` has `ClearAllValuesForTab` (clears popup, title, icon, badge text and colors, visibility) and a separate `ClearDeclarativeValuesForTab` (declarative show count and declarative icon). (Source: https://raw.githubusercontent.com/chromium/chromium/main/extensions/browser/extension_action.cc) Current `tab_helper.cc` no longer calls it, and the new call site was not found; so the Chrome navigation reset is `unverified` on today's source and needs an e2e check.

### 3. declarativeContent in Chrome; page_action in Firefox

Warning. `declarativeContent` has no permission warning. (Source: https://developer.chrome.com/docs/extensions/reference/permissions-list, read twice) The reference page says matching on URL or CSS needs no host permissions and no content script. (Source: https://developer.chrome.com/docs/extensions/reference/api/declarativeContent)

ShowAction. It sets the toolbar action to enabled while a rule's conditions match; elsewhere the action is greyed out and clicking opens the context menu instead of triggering the action. It works without host permissions. (Sources: https://developer.chrome.com/docs/extensions/reference/api/declarativeContent, https://raw.githubusercontent.com/chromium/chromium/main/chrome/common/extensions/api/declarative_content.json) For this to dim anything the action must start disabled. The `action` manifest key accepts `default_state` of `"enabled"` (default) or `"disabled"`; with "disabled" the action must be enabled programmatically to be clickable; enable and disable only affect whether the popup or `action.onClicked` fires. `default_state` is parsed only for the `action` key (error for `browser_action` and `page_action`). (Sources: https://developer.chrome.com/docs/extensions/reference/api/action, https://raw.githubusercontent.com/chromium/chromium/main/extensions/common/api/extension_action/action_info.cc) `action.isEnabled()` returns false for actions enabled only through `declarativeContent`. (Source: https://developer.chrome.com/docs/extensions/reference/api/action)

Consequence of the disabled route. A disabled action turns a toolbar click into the context menu, so a toolbar popup would not open on non-store tabs (inference from the quotes above). A Chromium Extensions thread from 2026-01-21 raises the same objection: the poster found `ShowAction` can enable the action but nothing disables it elsewhere; the only reply says `action.disable()` is per tab and not global, which makes the documented pattern hard to use without waking a worker on every navigation, dislikes that a disabled icon turns a normal click into a right-click-style menu, and suggests swapping the icon and letting the popup check the tab URL instead. The thread has no Chrome team answer and does not discuss `default_state`. (Source: https://groups.google.com/a/chromium.org/g/chromium-extensions/c/L2ynpbH08KM)

SetIcon. "Sets the n-dip square icon" for the page or browser action while conditions are met; the extension must already have an action. In `declarative_content.json` only `imageData` (ImageData or `{size -> ImageData}`) is defined; `path` is commented out with a TODO, although the description text still says "Exactly one of imageData or path must be specified". The reference page lists only `imageData` as a property. (Sources: https://raw.githubusercontent.com/chromium/chromium/main/chrome/common/extensions/api/declarative_content.json, https://developer.chrome.com/docs/extensions/reference/api/declarativeContent) An earlier read of the reference page reported `path` as supported; the source file contradicts that, so treat `path` as unsupported. Building ImageData from a packaged PNG needs canvas or `createImageBitmap` in an extension context (inference). Whether the serialized pixel data persists with the rule across restarts is `unverified`; docs only say rules persist.

Rules persistence and registration. Rules persist across browsing sessions; the page recommends `removeRules` then `addRules` during installation, and bulk operations because each one rebuilds internal data structures. (Source: https://developer.chrome.com/docs/extensions/reference/api/declarativeContent) The page's example sits in a `runtime.onInstalled` listener, which lives in the service worker, but the page makes no statement that a service worker is required. In Chromium's feature file `declarativeContent` and `action` are available to `privileged_extension` contexts, a set that is wider than the service worker. (Source: https://raw.githubusercontent.com/chromium/chromium/main/chrome/common/extensions/api/_api_features.json) Inference: rules could be registered once from an extension page such as an options page or popup, and the extension needs a background only if registration must run unattended at install or update. `unverified` in practice. Chrome's `declarativeContent` and `background` both have stable channel and no minimum manifest version. (Source: https://raw.githubusercontent.com/chromium/chromium/main/chrome/common/extensions/api/_permission_features.json)

Firefox. MDN has no `declarativeContent` page (the file path returns 404) and the Chrome incompatibilities page says the API "is not implemented". (Sources: https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/api/declarativecontent/index.md, https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/chrome_incompatibilities/index.md; the second was read by one fetch summary only). Firefox's `action` manifest key lists `browser_style`, `default_area`, `default_icon`, `default_popup`, `default_title` and `theme_icons`; there is no `default_state`. (Source: https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/manifest.json/action/index.md)

Firefox page_action with show_matches. Still supported in MV3: BCD lists `page_action` since Firefox 48, `show_matches` and `hide_matches` since Firefox 59, with the "MV2 only" note only on Chrome, Edge and Safari; the MV3 migration guide says Firefox keeps the page action API and key while Chromium and Safari merge it into `action`. (Sources: https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/manifest/page_action.json, https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/) It is hidden by default and shown for URLs matching `show_matches`; `hide_matches` overrides it and excludes `<all_urls>`. It renders "inside the browser's URL bar", not on the toolbar. (Sources: https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/manifest.json/page_action/index.md, https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/user_interface/page_actions/index.md) So it can show a second icon in the address bar on store pages with no JS, but it cannot dim the toolbar icon, and it needs its own popup.

### 4. Setting a tab-scoped action icon with no background

Content scripts cannot (section 2). The only other extension code that could run in a store tab is an extension page in an iframe injected by the content script, which needs `web_accessible_resources` with `matches` for the store.

Chrome. In Chromium's feature file `action` and `tabs` (so `tabs.getCurrent`) are limited to `privileged_extension` contexts. (Source: https://raw.githubusercontent.com/chromium/chromium/main/chrome/common/extensions/api/_api_features.json) `TabsGetCurrentFunction::Run` returns the tab of `GetSenderWebContents()` when its tab id is non-negative, otherwise an empty result with no error. (Source: https://raw.githubusercontent.com/chromium/chromium/main/chrome/browser/extensions/api/tabs/tabs_api.cc, first 100000 characters read) I could not confirm from source how that resolves for an extension iframe inside a web page. A search found community reports that a `chrome-extension://` iframe injected by a content script can use `chrome.tabs` (not primary). Status: `inference` that it works in Chrome; `unverified`; needs a test.

Firefox. A Mozilla xpcshell test for iframes created by a content script asserts "the created iframe should not be able to use privileged APIs (tabs)" and that `tabs` and `windows` are absent from the iframe's available APIs, while `browser.runtime.getManifest()` and `sendMessage()` work. (Source: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/toolkit/components/extensions/test/xpcshell/test_ext_contentscript_create_iframe.js) `tabs.getCurrent` reads only `context.tabId`; for an extension frame in a web page the parent-side `tabId` would resolve to the top-level tab's id, but that is moot when the `tabs` namespace is absent in the child. (Sources: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/browser/components/extensions/parent/ext-tabs.js, https://raw.githubusercontent.com/mozilla-firefox/firefox/main/toolkit/components/extensions/ExtensionParent.sys.mjs) Whether `action` is available in such an iframe was not found, `unverified`. The iframe also cannot reach a background (there is none) and runtime messages from a frame go to other extension frames only. (Source: https://developer.chrome.com/docs/extensions/reference/api/runtime) Conclusion: not viable on Firefox.

Costs of the iframe route (both browsers):

- Fingerprinting. By default no resources are web accessible because otherwise a site could fingerprint installed extensions; Chrome extension IDs are fixed, so any site can probe a listed resource; `use_dynamic_url: true` makes the URL per session. (Source: https://developer.chrome.com/docs/extensions/reference/manifest/web-accessible-resources) Firefox uses a UUID "randomly generated for every browser instance", which blocks that probe. (Source: https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/manifest.json/web_accessible_resources/index.md) `matches` limits who can load the resource: Chrome requires a path of `/*`.
- Attack surface. A web-accessible page can be loaded or framed by any matching site, and its `postMessage` traffic is visible to the page; MDN advises avoiding injection of `moz-extension:` URLs into web pages. (Sources: https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/manifest.json/web_accessible_resources/index.md, https://palant.info/2022/08/31/when-extension-pages-are-web-accessible/)
- Page effects. An extra frame per store page in Steam's DOM, subject to the page's own CSP for framing (not checked; MDN says web-accessible resources are not blocked by CORS or CSP, which covers Firefox's side only).
- Project fit (inference). The frame is a new composition root and a new surface, so it needs an ADR like a background does; it buys nothing over a background in Firefox and carries more risk than a background in both. (Source: local file AGENTS.md rules 3 and 11)

### 5. How uBlock Origin dims its icon

uBO is GPL; this section records the idea only. Source files are in https://github.com/gorhill/uBlock.

- Mechanism. uBO calls the toolbar action's `setIcon` per tab: `vAPI.setIcon(tabId, details)` resolves the tab and runs one line that passes `tabId: tab.id` plus an icon set chosen by state. (Source: https://raw.githubusercontent.com/gorhill/uBlock/master/platform/common/vapi-background.js; the call reads `browserAction.setIcon(Object.assign({ tabId: tab.id }, icons[state]))`)
- Icon sets. An `icons` array holds an "off" set (`img/icon_16-off.png`, `icon_32-off.png`, `icon_64-off.png`) at index 0 and the "on" set at index 1; `state` indexes it. The title reads "off" when state is not 1. (Source: same file, read twice with different prompts.) A separate `vAPI.setDefaultIcon(flavor, text)` sets the global icon (no `tabId`) for the loading state. Badge text, badge color and title use the same `browserAction` per-tab calls.
- Chromium path. On Chromium it preloads the PNGs into a canvas and passes `imageData` instead of `path`. (Source: same file.)
- Trigger. `updateToolbarIcon(tabId, parts)` in `src/js/tab.js` queues an update with `requestIdleCallback` (701 ms timeout) and `updateBadge` computes `state = pageStore.isNotTrusted() ? 1 : 0`, so "off" means filtering is switched off for the site (a trusted site), not "not a supported page". It runs on every tab bind (`onNavigation` for frame 0 in the `tabCommitted` context, `onNewTab`, `onUpdated`) and on `tabs.onActivated`. (Source: https://raw.githubusercontent.com/gorhill/uBlock/master/src/js/tab.js)
- Context. This is the Chromium MV2 manifest: `background.page`, permissions include `tabs`, `webNavigation`, `webRequest`, `<all_urls>`. (Source: https://raw.githubusercontent.com/gorhill/uBlock/master/platform/chromium/manifest.json) uBO always has a persistent page with those events and a per-tab state store, so it re-applies the icon on each navigation and activation. The manifest version string returned by the fetch looked out of place and is not reported.
- Takeaway (inference): the same shape is available to us with far less state: the "on" set per tab from a message, the "off" set as the manifest default.

### 6. Event page and service worker lifecycle cost of one message per store page load

Chrome. A service worker can be terminated after 30 seconds idle; events and extension API calls reset the timer (API calls since Chrome 110); a long-lived port keeps it alive from Chrome 114; a dormant worker is revived by an incoming event. The page says nothing about start-up cost. (Source: https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle) Handlers must be declared at the top level, "registered synchronously on initial script execution"; both `runtime.onMessage` and the service-worker `message` event work in extension workers, and the docs prefer extension messaging. (Source: https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/events)

Firefox. Event pages "load only when needed to respond to an event", unload after inactivity, keep listeners across unloads but lose other in-memory values; listeners must be registered synchronously at top level; message ports cannot keep an event page alive. MDN gives no number. (Source: https://raw.githubusercontent.com/mdn/content/main/files/en-us/mozilla/add-ons/webextensions/background_scripts/index.md) Bugzilla gives the default `extensions.background.idle.timeout` as 30 seconds (bug 1901294) and bug 1830767 (fixed in Firefox 117) set `EventManager.resetIdleOnEvent = false` by default, so event firing no longer resets the idle timer by default; the exact semantics were not read from source. (Sources: https://bugzilla.mozilla.org/show_bug.cgi?id=1901294, https://bugzilla.mozilla.org/show_bug.cgi?id=1830767) Firefox 106 added non-persistent MV2 pages; MV3 requires event pages. (Source: https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/)

Cost estimate (inference). One store page load means one cold start of the worker or page when none is alive, one `onMessage` dispatch, one `action.setIcon` call (which resets the Chrome idle timer), then idle until the 30 s timer ends. The handler keeps no state, so nothing is lost on termination. No primary source gives the cold-start time in milliseconds: `unverified`; measure it in the e2e run. The icon flips from dim to normal only after the content script runs and the background wakes, so a visible flash on store tabs is possible; `declarativeContent` has no such delay (inference). Send the message once per page load, and again on `pageshow` with `persisted` true, because a bfcache restore keeps the JS state and would not re-run the content script (inference; the bfcache clearing of tab-scoped icon state is `unverified`).

## Caveats and version notes

- All Firefox facts assume the project's floor of Firefox 140 and the current MDN text read on 2026-11-13. All Chrome facts come from the live developer.chrome.com pages and the Chromium main branch on that date.
- Fetch summaries are model-written. Two statements in this note come from a single fetch each and carry that risk: the Firefox incompatibilities line on `declarativeContent`, and the Bugzilla 1573659 status and date. The `declarativeContent` `path` claim was contradicted by the source file; the file was used.
- The Chrome tab-scoped icon reset on navigation is not in the current docs and was not found in current source. Test both browsers: load a store tab, confirm the icon is normal, navigate to a non-store URL, confirm it is dimmed, go back through bfcache, confirm it is normal again.
- A disabled Chrome action (`default_state: "disabled"`) changes click behavior; whether the Firefox disabled state dims the icon is not documented on MDN (the `action.disable` page says only "cannot be clicked"). Dimming by icon swap avoids both questions.
- Chrome `action.setIcon` rejects SVG; ship PNG sets (Chrome docs say icons are 16 DIP and recommend several sizes) or build imageData. MDN says Firefox page action icons accept SVG; for the shared build, PNG works in both.
- Do not add `tabs`, `webNavigation` or host permissions to solve this: each adds a warning (`tabs` and `webNavigation` read "Read your browsing history.") and AGENTS.md rule 3 forbids host permissions without an ADR.
- AGENTS.md rule 3 (no background without an ADR) and the Firefox `data_collection_permissions` key (see sibling note rq5) are project and AMO gates, not extra store review for the background key.
